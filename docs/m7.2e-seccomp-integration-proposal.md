# M7.2e decision proposal: socket-deny seccomp filter for `mind mcp`

Status: proposal 2026-11-08, SUPERSEDED by the implementation described in [sandbox-seccomp.md](sandbox-seccomp.md) (M7.2e). Differences: the filter is installed at the very start of `sandbox::enter` (a Git child of stage 1 was found unfiltered otherwise); x32 numbers are killed; a blocked `seccomp` query counts as required, not unsupported.

Original status: no product code changed. Basis: M7.2c/M7.2d tests (`tests/seccomp_isolation.rs`,
`tests/seccomp_compat.rs`, commit `c8d30b0`) and a reading of `src/cli/mod.rs` and `src/sandbox/mod.rs`.
Labels: VERIFIED (executed), REASONED (from code/kernel semantics), UNKNOWN.

## 1. Where it fits (code facts, REASONED from reading)
`mcp_command` (`src/cli/mod.rs`) runs in BOTH stages (stage 1 and the re-exec'd stage 2):
1. `sandbox::close_inherited_fds()` closes every descriptor above stderr, first thing.
2. `sandbox_state` -> stage 2: `verify_stage2` (canary probes, no stray fds, Git probe); stage 1: `sandbox::enter`:
   validate layout, build ruleset, `restrict_self`, canary check, `exec` self with `MINDSPACE_SANDBOX_STAGE2`.
`mind mcp` without roots (`NotNeeded`) and `--insecure-no-sandbox` never reach `enter`; every other CLI command never
reaches `mcp_command`.

**Integration point:** inside `sandbox::enter`, after the layout/ruleset checks and BEFORE `restrict_self`
(`ruleset.restrict_self()`), install the filter on the (single-threaded) stage-1 thread; stage 2 verifies it by
observation, like the Landlock canary. A filter survives `execve`, so stage 2, Git and the doctor self-test child inherit it
(VERIFIED: server `Seccomp: 2` after the re-exec; 13/13 Git invocations `Seccomp: 2`).
Why before Landlock: if the installation fails nothing has been restricted yet, so the existing `Outcome::Unavailable`
path (repository tools off, memory tools unaffected) applies without a half-confined process.
Scope = exactly the sandboxed path: no global CLI filter, `mind model install` (needs sockets) and all other commands stay
unfiltered (VERIFIED in M7.2d: the CLI workloads were only filtered because the test forced it).

## 2. Descriptors (question 2 and 3)
* Open at stage 1 after `close_inherited_fds`: 0, 1, 2 only (REASONED; stage 2 FAILS the start if anything above stderr is
  open: `verify_stage2` -> exit 78). A socket created before the filter would remain connectable (VERIFIED, dormant fd probe), which is
  why the filter MUST be installed after `close_inherited_fds` and Mindspace MUST NOT open any socket before it (it opens none;
  the only `ureq` use is `mind model install`).
* stdio can itself be a socket handed over by a client (REASONED, not tested): that is the MCP transport and cannot be
  closed. Document: "already open descriptors, including stdio, stay usable".
* Stage 2 additionally asserts: `Seccomp: 2` in `/proc/self/status` AND `socket(AF_UNIX|AF_INET|AF_INET6)` fails with
  EACCES/EPERM (behavioural canary, not the env marker).

## 3. Other ways to a socket despite `socket()` denied
| Path | Status |
| --- | --- |
| `io_uring_setup` (IORING_OP_SOCKET) | denied in the filter (VERIFIED EACCES) |
| 32-bit/compat syscalls, `socketcall` | foreign arch is KILLed by the arch check (REASONED; killing is fail-closed, not an escape) |
| `socketpair` | stays allowed: anonymous AF_UNIX pair, no external peer (VERIFIED works) |
| receiving a socket via `SCM_RIGHTS` over stdio/inherited fd | open (REASONED) |
| `pidfd_getfd` / `ptrace` / `process_vm_*` on a same-user process that holds sockets | NOT blocked by the filter; Yama `ptrace_scope>=1` blocked it here (VERIFIED EPERM, scope=1). With scope 0 UNKNOWN/likely open. Proposal: add `pidfd_getfd`, `ptrace`, `process_vm_readv/writev` to the deny list, with their own compat tests (Git does not need them, REASONED) |
| `unshare`/new namespaces | the filter stays in force inside them (REASONED) |
| `/proc/<pid>/fd/<n>` open of a socket | ENXIO by kernel design (REASONED, not tested) |
Not covered by a socket filter at all: signals, filesystem (Landlock), reading `/proc`. No claim of network or IPC isolation is made; the
claim is "no NEW sockets can be created by the server or its children".

## 4. Error policy (question 5; no silent degradation)
| Situation | Behaviour |
| --- | --- |
| Architecture without a verified audit constant (today: anything but x86_64, aarch64; aarch64 untested, see 5) | filter NOT activated; stderr line at start and `mind doctor`: `seccomp: not applied (unsupported architecture)`. Repository tools keep running under Landlock only |
| Kernel reports no filter support (probe `No`) | same wording, `not applied (kernel)` |
| Supported arch, install fails (EPERM/EACCES/ENOSYS from a container policy, EINVAL, ENOMEM) or probe `Unknown` | FAIL CLOSED: `Outcome::Unavailable(reason)` -> repository tools OFF, loud stderr, doctor `warn` with the errno; never fall back silently |
| Filter installed but stage-2 canary/`Seccomp:` check fails | exit 78 (same as the Landlock canary) |
| User wants it off | no new opt-out in the first step (the existing `--insecure-no-sandbox` already drops all kernel sandboxing). A separate switch is a later, explicit decision |
"Not applied" on an unsupported platform is explicit and diagnosable; it is not an install failure, and the report must not show
the socket channels as enforced then.

## 6. Git and other children (question 8)
Children inherit the filter and cannot remove it (`NO_NEW_PRIVS`, VERIFIED inheritance). The Git hardening already disables
network, hooks and fsmonitor (`src/ingest/git.rs`: `core.fsmonitor=false`, no remote helpers; REASONED), and the compat run
(ingest, outline, doctor self-test, Git metadata) behaved identically with the filter (VERIFIED, x86_64). UNKNOWN: Git builds or
configurations that open a socket on purpose, rare Git sub-commands outside the tested set.

## 7. `mind doctor` (question 9)
* Server self-report: replace the free-text sandbox description with an additional typed field in the `repo_outline`
  `sandbox` payload, e.g. `{"landlock":{"abi_min":3},"seccomp":{"state":"enforced|not_applied|failed","arch":"x86_64","denied":["socket","io_uring_setup",...]}}`
  (additive; the existing string stays). The doctor reads the typed field, not text.
* `capabilities.product.uses_seccomp` becomes dynamic from that field, never from the ABI or a constant alone; `sandbox::DECLARED.seccomp` flips
  with the implementation. Channels `tcp`, `udp`, `unix_path_sockets`, `unix_abstract_sockets` become `enforced` ONLY
  if the self-test child reports `seccomp.state = enforced`; each gets a note "new sockets only; inherited descriptors remain".
  `signals` and `filesystem` semantics unchanged.
* `seccomp_mode_of_doctor_process` stays informational (it can be an inherited container filter).

## 8. Required regression tests
1. Unit: policy table (arch x kernel probe x install result -> {enforced, not_applied, failed}); fake installer errors; no silent downgrade.
2. `mind mcp` with a root: server `Seccomp: 2`; `socket()` fails in the server (via a test-only probe or `/proc`); Git children `Seccomp: 2` (shim).
3. Stage 2 started with the marker but without the filter -> exit 78.
4. Stray socket fd inherited into `mind mcp` -> closed or start refused; never usable (dormant-fd regression).
5. Every CLI command except `mcp` runs with `Seccomp` unchanged (shim on `ingest`/`scan`); `mind mcp` without roots unchanged.
6. Pre-existing container-like filter: stacking works; a filter that blocks `seccomp()` -> tools OFF, warn, no panic.
7. Full existing suites (`mcp*.rs`, `ingest_confinement.rs`, `doctor.rs`, `sandbox_failure_modes.rs`) green with the filter on, plus the M7.2d matrix against the real wiring.
8. Doctor JSON: backward compatibility; `enforced` only with typed evidence; unsupported arch reports `not_applied`.
9. Watchdog/leftover-process checks as in M7.2d; timeout/kill of the server and the ingest path under the filter.
10. aarch64 job (blocks enabling there).

## 9. Open risks
* Sockets and descriptors that exist anyway: stdio sockets, `SCM_RIGHTS`, same-user `pidfd_getfd`/ptrace with Yama off.
* Filter is per thread without TSYNC: relies on stage 1 being single-threaded (the existing Landlock design assumes the same). Use TSYNC or assert one thread.
* Denylist rather than allowlist: new socket-creating syscalls in future kernels would pass; a long-term option is a syscall allowlist (large compat cost, not proposed now).
* Real MCP clients under the filter, other kernels, other architectures, containers: UNKNOWN.
* User-visible failure on hardened containers (tools OFF); needs a documented remedy text.
* It adds a second sandbox layer to a preview whose security model is already narrow: documentation must keep saying "no network or IPC isolation".

## 10. Recommendation
**NEEDS MORE EVIDENCE, leaning GO for a first step limited to x86_64.** Smallest next step (M7.2e implementation): the stage-1 install +
stage-2 verification + typed doctor field + error table above, activated only on x86_64, with tests 1-9. aarch64 stays
off until a CI job passes. Not proposed: any global filter, any socket opened before the install, any automatic enabling on untested
architectures, any weakening of the deny list to make a test pass.
