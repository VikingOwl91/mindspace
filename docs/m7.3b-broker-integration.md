# M7.3b.3a: persistent stage-1 broker in the real `mind mcp` startup

Status: implemented on `integ/m7.3b3a-stage1-broker` (worktree `mindspace-wt/broker-integ`), uncommitted, from `176524b`.
Opt-in and hidden (`mind mcp --broker`); **no MCP tool uses it**. Labels: VERIFIED (test or measurement here), REASONED, UNKNOWN.
Builds on `docs/m7.3b-broker-architecture.md`; the A0 assurance limit is unchanged.

## 1. Actual process topology (VERIFIED, pids from a release run)

```
mind mcp --allow-root P --grants --broker           (stage 1, unconfined)
  1. seccomp socket-deny installed (this thread, single-threaded)
  2. Landlock ruleset built
  3. socketpair; fork ──► BROKER (pid 203671)  keeps: socket-deny filter (inherited), NO Landlock domain,
  4. restrict_self                                   dumpable=0, no-new-privs, stdin/stdout -> /dev/null,
  5. exec stage 2 (same pid 203656)                  every fd closed except its channel end
       = FRONTEND: Landlock + seccomp, holds the DB, one extra fd (CLOEXEC) = its channel end
BROKER cgroup  .../app.slice/app-graphical.slice/mindspace-203671-1/supervisor
FRONTEND cgroup .../kitty-10144-0.scope (unchanged)
worker 203788: .../mindspace-203671-1/op-01a1bfad-...  seccomp 2, nnp 1, tracer 0, CapEff 0, cleanup=cgroup
```
The broker is forked AFTER the filter and BEFORE `restrict_self`; a child of a confined process could never be less confined.
It is the frontend's child, so it is found as the frontend's only child (`SO_PEERCRED` on a socketpair names the creator = the
frontend, not the broker: a harness bug found and fixed during this work).

## 2. Descriptor and authority boundaries

* The frontend inherits exactly one extra descriptor. Stage 1 passes its number in `MINDSPACE_SANDBOX_BROKER_FD`; stage 2 keeps
  it only if it is an `AF_UNIX` `SOCK_STREAM` socket (`broker_fd_from_env`), refuses every other stray descriptor in
  `verify_stage2` as before, and sets close-on-exec unconditionally so Git children never inherit it (VERIFIED: `self` reports
  `broker_fd_cloexec: true` as startup left it).
* The broker reads the grant store and the static roots itself, per operation (`CombinedAuthority`). The frontend names a path;
  the closed IPC vocabulary has no grant, access, ttl, fd or limit field (VERIFIED: five injections, each on a fresh frontend,
  refused as unreadable, no descriptor handed over). The frontend still cannot read the grant store or a dynamic root.
* The frontend's view of the broker (VERIFIED): `kill(pid,0)` = EPERM (Landlock signal scope), `ptrace` = EACCES,
  `/proc/<pid>/mem` and `environ` = EACCES (not dumpable). On a kernel without the signal scope (ABI < 6) the frontend could
  signal the broker (a denial of its own dynamic operations only; REASONED, not tested).
* No sandbox invariant was weakened: the ruleset, the filter, the canary and `verify_stage2`'s stray-fd rule are unchanged
  except for the one validated descriptor. Landlock rules for the frontend are untouched.

| # | Requirement | Result |
|---|---|---|
| 1 | static authorized root through the broker | extracted and persisted by the frontend; worker gone; broker-observed seccomp 2 / nnp 1 / cgroup `op-...` |
| 2 | root approved after the frontend started | refused, then `mind grant add`, then extracted and persisted, same frontend process; revoke refuses the next operation |
| 3 | unauthorized root | other directory, parent, subdirectory: "not authorized" |
| 4 | frontend cannot read the dynamic root | `read_dir` and `read` of the dynamic root = EACCES; of the static root = ALLOWED |
| 5 | worker cannot read DB / grant store | symlinks to the database and every grant-store file inside the dynamic root: none of their bytes (`SQLite format`, grant id, `granted`) in the result; the frontend cannot read the store either |

Stand-in workers are shell scripts started by the broker through a test-only hook (feature `spawn-gate`: absent from a plain
build, enabled only for `cargo test`). The frontend is never a stand-in.

## 4. cgroup lifecycle review

* **Placement.** The broker moves only itself (not the frontend) into `<base>/supervisor` and puts operations beside it. A
  cgroup holding processes cannot delegate controllers, so the broker tries its own cgroup first, then the parent (sibling).
* **systemd user manager (VERIFIED with `systemd-run --user`, Delegate=yes and Delegate=no, plus a scope):** the unit's own
  cgroup lists `memory pids` but cannot delegate them (its main process lives there); mkdir succeeds in it and in `app.slice`;
  the broker therefore ends up as a sibling under `app.slice` with `memory`/`pids`. All 8 tests pass in both modes.
  `Delegate=` made no observable difference here because the user manager's tree is already user-writable.
* **Consequence to document:** the broker and its workers sit OUTSIDE the unit's cgroup, so the unit's `MemoryMax=`,
  `TasksMax=` and `KillMode=control-group` do not cover them. They end because the broker exits when the frontend's channel
  closes (VERIFIED: frontend SIGKILL, normal exit), not because systemd kills them.
* **System-level services: UNKNOWN (no root here).** REASONED: an unprivileged `User=` service without `Delegate=yes` cannot
  create cgroups, the broker exits with "cannot start (no cgroup delegation?)" and the frontend gets an error for every
  dynamic operation. With `Delegate=yes` the unit's own cgroup is writable, so `cgroup.kill` works, but no controllers can be
  delegated (memory/pids limits for operations are then refused, never silently skipped). **Required configuration:** run under a
  manager that delegates (a user service, or `Delegate=yes`), and set resource limits on the unit if aggregate accounting is
  wanted there. The test-only parent override made the real kernel answer EACCES on `/sys/fs/cgroup`: fail-closed VERIFIED
  (no worker started, rows unchanged, frontend alive, diagnostic on stderr).
* **Cleanup (VERIFIED):** normal exit and frontend crash remove the broker's tree. Broker crash (SIGKILL): the worker dies with
  it (PDEATHSIG), the frontend gets an error, **an escaped `setsid` descendant survives** and keeps the worker channel open, so
  the frontend only notices at its own wall-clock limit; the next broker start sweeps dead brokers' trees and kills what is left
  (VERIFIED). Between the crash and the next start the descendant runs.
* **Accounting.** `memory.peak` of the operation cgroup is reported when the memory controller is present; `memory.max` was
  verified at library level (`tests/broker.rs`). The `--broker` path configures no limit yet (no approved values).
* **Not done:** a surviving-broker watchdog outside the process (systemd or an external reaper) for the crash window.

## 5. Remaining limitations

1. Not wired into any MCP tool; the gate harness is the only caller of the channel in the frontend.
2. Running operations are not revoked (only the next one is); bounded by the broker's wall clock and the frontend's.
3. Broker crash leaves escaped descendants until the next start (section 4).
4. One frontend connection, sequential operations; the zombie of an exited broker stays until the frontend exits.
5. Landlock is not externally observable; a compromised worker binary is out of model; fresh-parse correctness is the
   documented residual trust boundary.
6. Kernels without the Landlock signal scope let the frontend signal the broker (availability only).
7. Startup failure after the fork (`restrict_self` or `exec` failing) is REASONED to end the broker (its channel closes with
   stage 1); not exercised by a test.
