## 1. The failure, reproduced (before the change) — VERIFIED

Real `mind mcp --allow-root P --grants --broker` frontend; a broker-managed stand-in worker (test-only hook) that starts a
descendant in a new session (`setsid`); `SIGKILL` to the broker. Sampled with `/proc` (`reproduce_broker_sigkill_timeline`):

| Event | Observation |
|---|---|
| process exit | broker: gone within 5 ms |
| reaping | broker: **zombie (`Z`) indefinitely**, its parent is the frontend and never waits. Worker: exits within 5 ms (PDEATHSIG) and is reaped by pid 4481 = the user manager `systemd` (a subreaper) |
| descendants | worker's `sleep` and the `setsid` descendant: **alive**, `ppid 4481` (adopted by that subreaper, still running), still in `.../mindspace-<pid>-1/op-<id>` (`cgroup.procs` = 2) |
| cgroup removal | never: the `op-<id>` directory, `supervisor` and the tree stay |
| the frontend | no EOF on the worker channel (the descendant holds it); it only noticed at its own wall-clock limit (20 s in this run) |

Three different things, all measured separately: exit (ms), reaping (broker never, worker immediately by someone else's
subreaper) and cgroup removal (never). A subreaper does not terminate anything: pid 4481 adopted the survivors and left them running.

Why B: the only components that can still act after the broker's SIGKILL are its parent, its siblings or the kernel. The
kernel has no cgroup-v2 "kill on owner death". The parent is the one place that is outside the broker's failure domain, needs
no new authority, and already receives the death notification.

## 3. The implemented correction

```
stage 1 ─fork─► intermediate (takes a pidfd of the frontend, forks the watchdog, exits; stage 1 reaps it)
                  └─► WATCHDOG (NOT the frontend's child; outside Landlock; socket-deny filter; subreaper; no IPC;
                      parses nothing; names itself `mind-wd-<frontend pid>`)
                   │  creates the cgroup tree (fails closed), moves itself into <base>/supervisor,
                   │  enables controllers, forks ─► BROKER (PDEATHSIG=SIGKILL; adopts the tree, does not own it)
                   │  waits (poll on two pidfds) on the BROKER and on the FRONTEND
                   └─ broker ended: kill every op-* cgroup (cgroup.kill), reap what was orphaned to it, wait until
                      they are empty, remove them and the tree, exit.
                      frontend ended first: 3 s for the broker to end its operations by itself, then SIGKILL, same cleanup.
```
* The watchdog holds no channel: the broker end of the frontend socketpair reaches the broker through the fork and the watchdog
  closes its copy. The frontend's authority is unchanged (same single descriptor, same Landlock rules); `sandbox/` gains only
  the call target (`watchdog_main` instead of the broker).
* Required kernel facilities (`cgroup.kill` 5.14, `pidfd_open` 5.3, a writable cgroup v2 subtree) are checked at start; any
  missing facility ends the watchdog before a broker exists, with `mind broker: cannot start (no cgroup delegation?): ...` on stderr.
* The broker is the watchdog's child, so the watchdog reaps the broker. The watchdog itself is reparented by the double fork to
  init / the nearest subreaper, so it is never a zombie of the frontend (the first version was: VERIFIED `Z` until fixed).
  The frontend needs no change. It *could* reap a child watchdog (`waitpid` needs no filesystem, signal or socket right: VERIFIED
  in a throwaway experiment) but would need the pid and production code, and `waitpid(-1)` would race with its Git children.
* **Placement (containment first).** The tree is created INSIDE the cgroup the process started in, so a service manager that kills
  the unit's cgroup also ends the tree even if the watchdog was killed (section 5). Such a cgroup cannot delegate controllers
  (it holds the frontend), so per-operation `memory.max`/`pids.max` are unavailable there and a configured limit is refused
  (never skipped). When a limit is configured (`limits_requested`, today only the test hook; the product configures none yet) the
  tree goes beside the original cgroup, where the parent can delegate controllers, at the price of leaving the unit. Aggregate
  limits inside a unit are then the unit's own (`MemoryMax=`, `TasksMax=`), which cover frontend, broker and workers together.

## 4. Kernel evidence (real `mind mcp`, real Landlock/seccomp/cgroups)

Latencies are from the first process-exit signal until every process is **reaped** (gone from `/proc`, not zombie) and the
cgroup tree directory is **removed**, polled at 200 µs; debug and release builds, interactive scope and `systemd-run --user` with `Delegate=yes` and `Delegate=no`.

## 5. systemd findings (VERIFIED in the user manager; system manager UNKNOWN: no root here)

Reproduce with `tests/scripts/systemd_unit_containment.sh` (needs the hook-enabled binary that `cargo test --no-run` leaves at
`target/debug/mind`). The real frontend runs as a transient user service; the watchdog is SIGKILLed; then `systemctl --user stop`.

| Placement of the tree | Delegate | after watchdog SIGKILL and unit stop |
|---|---|---|
| beside the unit (the first version's default; forced by a limit) | yes / no | escaped descendant **still alive** (outside the unit) |
| inside the unit (current default) | yes | descendant **gone** at stop (`KillMode=control-group`, 42-47 ms) |
| inside the unit (current default) | no | descendant **gone** at stop (6 ms) |

* So the watchdog-SIGKILL leak is bounded by the lifetime of the unit using only systemd's own mechanism and no further
  supervisor. While the unit keeps running after the watchdog was killed, the leak persists (until the unit stops or the next start sweeps it).
* The whole MCP-path suite (15 tests) passes under `systemd-run --user` with `Delegate=yes` and `Delegate=no`; no tree is left.
* Inside the unit, the unit's own `MemoryMax=`/`TasksMax=` apply to the whole tree. Per-operation cgroup limits need the
  sibling placement and therefore leave the unit.
* `Delegate=no` worked in the user manager only because its subtree is user-writable; it does not say anything about system units.

## 6. Unsupported or degraded deployments (kept separate on purpose)

1. cgroup v1 or a hybrid hierarchy: not supported (no `cgroup.kill`); the broker does not start.
2. Kernels older than 5.14 (`cgroup.kill`) or 5.3 (`pidfd_open`): not supported; explicit start error.
3. System services without `Delegate=yes` (or without a user manager): the watchdog cannot create a cgroup and exits 71; every
   dynamic operation fails explicitly ("the broker is not available (it never started or has exited)", VERIFIED). REASONED for a real system unit; the identical kernel refusal was produced and verified by the parent override.
4. System services with `Delegate=yes` and the frontend inside the unit's cgroup: `cgroup.kill` works, controllers cannot be
   delegated while a process lives in the same cgroup, so memory/pids limits requested for operations are refused (never silently dropped). REASONED.
5. Hardened containers that mount cgroup read-only: same as 3.
6. Non-Linux: no sandbox, no broker.

## 7. Remaining risks

1. **Watchdog SIGKILL (double fault).** Broker and worker follow (PDEATHSIG), the frontend gets an error, but an escaped
   descendant survives until the unit stops (systemd, when the tree is inside the unit), or the next start sweeps it. There is
   no always-running mechanism that bounds it further without another supervisor, which was deliberately not added.
   The frontend cannot signal the watchdog where the Landlock signal scope exists (ABI 6+).
2. A same-user unrestricted process can kill the watchdog; outside the A0 guarantee, as before.
3. Frontend death with a wedged broker: the watchdog waits 3 s, then kills it (VERIFIED for the frontend-kill path).
4. The 10 s ceiling of the watchdog's cleanup loop: an uninterruptible process leaves its cgroup; swept at the next start.
5. The watchdog's reaper is init / the nearest subreaper; in a container whose pid 1 does not reap, it stays a zombie. REASONED.
6. The sweep only covers trees at the placement the new process uses: a tree left by an older sibling placement is not swept (found and removed by hand during testing).
7. Per-operation limits are not wired in the product path; they force the sibling placement (leaving the unit).
8. Running operations are still not revoked, and no MCP tool uses the broker.
