# M7.3b.2b gate: can the sandboxed MCP frontend run the extraction worker?

Branch `feat/m7.3b2b-frontend-spawn-gate` (from `6b0fdb1`), uncommitted. Labels: **Measured**, **Reasoned**.
Harness: the production `mind mcp --allow-root` startup (stage 1, stage 2), whose last step is replaced, in this
branch only, by `worker::gate` (it runs the production worker client against a root authorized by the same `McpConfig`
and persists through the production `persist`). Nothing about the sandbox is faked or weakened.

## A. The actual topology
| Question | Answer (code read, then confirmed by the tests) |
|---|---|
| When is seccomp applied | Stage 1 (`enter_with_args`), first thing: the socket-deny filter on the single thread that later execs. Stage 2 inherits it and re-verifies. |
| When is Landlock applied | Stage 1, after the filter: rules from `Plan::rules()` (system dirs, DB dir rw, models ro, each root by verified descriptor, own binary FileExec, own `/proc/<pid>`), `restrict_self`, canary check, then `exec` of itself = stage 2. |
| Who owns the root descriptor | The stage-2 frontend: it opens a root per tool call (`authorize` + `Anchor::open`). The worker gets a duplicate. |
| Who can read the grant store | Only stage 1, before it confines itself (it passes the resolved roots to stage 2 as arguments). Stage 2 has no rule for it; roots overlapping it are refused. The worker never sees it. |
| Can the frontend run the worker | Its own binary (FileExec) and anything under `/usr`: yes (Measured: the worker started). Any other binary: no (Measured: a script in a temp directory fails with `Permission denied`, `/nonexistent` with `No such file`). |
| IPC channel | `socketpair(AF_UNIX)` is allowed (Measured); only `socket()` is denied by the production filter. A channel cannot be denied by the current sandbox. |
| Fork/spawn | Allowed (no rule or filter entry stops it). |
| What the worker inherits | The frontend's Landlock domain (DB directory read/write, rw roots, its own `/proc` entry only), the seccomp filter, no-new-privs; descriptors 0-2 plus the two it was given (it closes everything above 4 first thing); a cleared environment. It then adds its own domain and filter: its effective authority is the INTERSECTION, so the worker's read-only root beats the frontend's rw root and the DB directory is not reachable (Measured). |

Trust boundaries: the frontend (holds the database and rw roots, serves MCP) trusts nothing from the worker; the worker (parses
untrusted repositories) holds read-only access to one root and nothing else. A compromised frontend is not stopped by the worker
design (that is the existing MCP sandbox's job); a compromised worker cannot write the database, the roots or reach the network.

## B. Result of the real frontend-spawn test
Final state (7 tests in `tests/frontend_spawn_gate.rs`, all pass): the frontend starts the worker, the hello arrives (4 ms), the
small directory is extracted, the stream is validated, the result is persisted by the frontend, the worker exits with code 0
and its process is gone.

What had to change before it worked (the unchanged worker slice fails closed at every step, Measured in this order):
1. `exit 78: refusing to install the seccomp filter: expected exactly one thread, found None`: the worker counts threads by
   reading `/proc/self/task`, which the inherited domain does not allow (only the frontend's own pid entry is covered).
   Worker-side fix: install the filter with `SECCOMP_FILTER_FLAG_TSYNC` (all threads, no `/proc` read).
2. The seccomp verification read the mode from `/proc/thread-self/status` (same denial). Fix: fall back to
   `prctl(PR_GET_SECCOMP)`, the kernel's own answer for the thread.
3. Listing `/proc/self/fd` to close stray descriptors silently returned nothing (a fail-open in `open_fds_above_stderr`,
   noted); the worker now closes by `close_range` without `/proc`.
4. The parent's check of `/proc/<worker>/status` fails inside the frontend (`Seccomp: None`): a confined frontend cannot read
   another process's `/proc` entry. This cannot be fixed without widening the frontend's rules; the client option
   `verify_via_proc = false` leaves the worker's own hello (all probes, observed by the worker after confinement) as the only
   evidence. This is a real loss of independent verification, see D.
5. Two defects of the slice found on the way (fixed): closing all descriptors above 4 in the child before `exec` also closed
   std's exec-error pipe, so a failed `exec` aborted the child and looked like a started worker; and reading the worker's
   stderr after the kill waited for end of file, which hangs forever if a descendant escaped the process group holding the pipe.

## C. Failure paths
| Case | Result | Expected denial or defect |
|---|---|---|
| worker executable outside `/usr` and not the frontend's binary | `cannot start the extraction worker: Permission denied (os error 13)` | expected denial |
| nonexistent executable | `No such file or directory` | expected |
| root not authorized / outside the roots | rejected by `authorize` before any spawn | expected |
| channel creation | `socketpair` allowed, `socket(AF_INET)` EACCES | the sandbox cannot deny the channel |
| a stand-in worker without its own sandbox | inherits the frontend domain: can read the DATABASE, cannot read `/etc/passwd` | shows why the worker must narrow itself |
| a repository symlinked to the database | the real worker returns none of its bytes although the frontend may read it | expected |
| directory descriptor from outside the frontend's domain (`landlock_fd_probe`) | `open`, `openat(dirfd)` and listing through the descriptor: EACCES; only descriptors of files opened beforehand stay readable | an fd does NOT override a Landlock domain |
| worker timeout (1.5 s, busy parse) | `timed out`, worker gone, frontend alive | expected |
| worker SIGKILL from outside | `killed by signal 9`, frontend alive, worker gone | expected |
| frontend SIGKILL | worker gone within the poll window (pdeathsig) | expected |
| descendant that called `setsid` | SURVIVES the group kill (Measured) | limitation, not fixed here |

## D. Classification
**A, with conditions** for roots that were in the frontend's sandbox at start (`--allow-root` and grants resolved in stage 1).
The worker's isolation is not weakened (its own domain and filter apply on top; every confinement probe passes inside the
frontend); the changes made to the worker's self-checks are equal or stronger (`TSYNC`, `close_range`, `prctl`). Conditions and limits:
* The authority boundary is the frontend's own: the worker can only ever read roots the frontend's domain covers. A directory
  descriptor opened outside does not help (Measured above). Roots approved after the frontend started (dynamic grants,
  just-in-time) cannot be served by a child of the frontend; they need the **broker outside the frontend's Landlock domain** to
  open the root and spawn the worker. For those the broker is a hard dependency; for static roots it is not.
* Independent verification by the parent is lost inside the frontend (item B4): only the worker's own report remains. A broker
  outside the domain (or the frontend with a read rule it cannot have) would restore `/proc` verification.
* Processes that leave the group are not cleaned up; a cgroup (or subreaper) is needed.
* Between `exec` and the worker's confinement the worker (our code, no untrusted input yet) holds the frontend's authority.

## E. Verdict for the context exchange
GO for implementing the context exchange (it is independent of who spawns the worker, and the spawn path now works for static roots),
with these carried requirements: the broker for dynamic roots and independent verification, process-tree cleanup beyond the group,
and a decision whether to keep `verify_via_proc = false` as the frontend's mode.

## Harness isolation and `verify_via_proc`

* The `MINDSPACE_SPAWN_GATE` entrypoint (`worker::gate`, hook in `mcp_command`) is compiled only with the
  feature `spawn-gate`. The feature is switched on solely through a self dev-dependency in `Cargo.toml`, i.e. for
  `cargo test` builds; a plain `cargo build [--release]` contains neither the hook nor the environment lookup
  (checked with `strings` on the release binary, see the commit notes). An environment variable alone cannot
  activate it in a production binary.
* `WorkerConfig::verify_via_proc = false` is **not** independent confinement verification. The parent then
  relies on the worker's own hello (seccomp mode, probes). It defaults to `true` and is used only by the gate
  harness; production wiring must not turn it off until a broker outside the frontend's Landlock domain
  verifies `/proc/<pid>/status`.
