# M7.3b hardening gate: Part D findings (design only, no product change)

Evidence labels: VERIFIED = observed by running code; REASONED = argued from
code/kernel semantics; UNKNOWN = not tested.

## D1. Can the frontend be non-dumpable without breaking Git and MCP?

Experiment (throwaway edits, reverted, nothing committed) on `main` = cbca449:
`prctl(PR_SET_DUMPABLE, 0)` in the MCP frontend after `close_inherited_fds`.

| Variant | Result |
|---|---|
| A. non-dumpable, Git unchanged (`cmd.current_dir("/proc/<pid>/fd/N")`) | VERIFIED: 6 of 9 `mcp_ingest_timeout` tests fail: `cannot run git: Permission denied (os error 13)` (chdir in the child before exec). Baseline without the patch: 9/9 pass. |
| B. non-dumpable, `git -C /proc/<pid>/fd/N` | VERIFIED: still fails (4 of 9): `fatal: cannot change to '/proc/<pid>/fd/6': Permission denied`. Dumpable is reset by exec in the child, but the *target* is the parent's `/proc/<pid>/fd`, whose access check depends on the parent's dumpability. |
| C. non-dumpable, anchor fds inherited into the git child (CLOEXEC cleared in `pre_exec`), paths rewritten to `/proc/self/fd/N`, `-C`, `GIT_DIR`, `GIT_COMMON_DIR` likewise | VERIFIED: `mcp_repo_tools` 37/37, `mcp_ingest_timeout` 9/9, `mcp` 9/9 (1 ignored as before), `doctor` 5/5 pass. One failure in `sandbox_failure_modes` (`an_inherited_descriptor_to_an_outside_file_does_not_survive_into_the_server`): the test reads `/proc/<server>/fd`, which non-dumpable correctly forbids. That is a loss of external introspection, not a regression of the confinement; the test would need another observation channel (REASONED). |

Conclusion: yes, feasible, but only with variant C. The root cause of F3 is
that the git child resolves the parent's `/proc/<pid>/fd/N`, which needs the
parent dumpable. C removes that dependency; it changes how every anchor path is
handed to Git (a fd-inheritance contract) and it is not a one-line hardening.
UNKNOWN: whether this holds for `git` builds other than the one on this host,
and for the file-ingest path (`/proc/<pid>/fd` is also used by `confined.rs`
for the process's own reads, which stay fine because `/proc/self` is readable
for a non-dumpable process by itself, REASONED, not exercised separately).

Recommendation: do not set non-dumpable on the current frontend. For the
production *worker* (which does not spawn Git children if Git runs inside it
with inherited fds, or does spawn them with variant C) it is the right default.

## D2. Why does Git ingestion write the marker?

`GitReader::repository_id()` (`src/ingest/git.rs`) reads
`<common_dir>/mindspace-repository-id` and creates it with `O_EXCL` if it is
missing. The marker is Mindspace-local identity: it survives moving or renaming
a repository, while a fresh clone gets its own id. It is not derived from Git
data because no Git property is both stable across moves and unique per clone
(remote URLs change, the root commit is shared by forks and clones). If it cannot
be persisted ingestion fails on purpose ("refusing to guess"), because a silently
created second identity would split history in the database.
VERIFIED by reading the code and `docs/decisions.md`; the creation is the only
write in Git extraction.

## D3. Can the marker leave extraction or become read-only?

Facts: `existing_repository_id()` already reads without creating. The extraction
split (M7.3b) leaves `repository_id()` inside extraction, so an extraction
process needs a rw root only for the first ingest of each repository.

Options (all REASONED):
1. **Two-step first ingest.** Extraction calls `existing_repository_id()`. If
   `None`, it returns `NeedsIdentity` to the frontend; the frontend (already
   trusted, holds the write grant) creates the marker, and the extraction is
   re-run read-only. Cost: one extra round trip on first ingest only. The marker
   write stays atomic (`O_EXCL`), the worker never needs write access.
2. **Identity in the database, not in the repository.** Key the id by
   (canonical path + device/inode of `common_dir`). Removes the write but breaks
   the documented "survives moving" property; a design change, not a hardening.
3. **Marker created at grant time.** Granting a repository (ADR-030) creates
   the marker as part of the grant, with the user's explicit approval of the
   write. Extraction is read-only by construction afterwards.

Recommended: 1 or 3. 3 matches the grant model best (the write is an
explicit, auditable approval step); 1 is the smaller change.

## D4. How a read-only grant for Git ingestion would work

- Grant record gains an access level (`read`), the marker is guaranteed to exist
  (D3.3) or created by the frontend (D3.1).
- The worker gets the repository as a *read-only* Landlock path beneath, plus the
  git binary's runtime directories (F1 fix), and no write rule. Git commands
  are pinned by `GIT_DIR`/`GIT_COMMON_DIR`; with `core.fsmonitor`, hooks,
  alternates and pager already neutralised (`PINNED_CONFIG`).
- Git can still want to write: `index` refresh is not done by the read-only
  commands used (`for-each-ref`, `cat-file`, `rev-parse`, `ls-tree`; REASONED
  from the command list), and `gc.auto=0`, `maintenance.auto=false` are set. If
  a git command tries to write it fails with EACCES, which is the intended
  behaviour. UNKNOWN: the full command list under a ro rule has not been run
  end to end; do that first in the production worker's test suite.
- Linked worktrees / `commondir` outside the root need their own read grants.
  The current pinned model already resolves both anchors, so this is a rule
  per anchor, not a new mechanism (REASONED).
