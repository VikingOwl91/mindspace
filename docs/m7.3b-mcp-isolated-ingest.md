# M7.3b.4: `repo_ingest_isolated`, the first opt-in MCP directory ingestion through the broker

Status: implemented on `feat/m7.3b4-mcp-broker-ingest` (worktree `mindspace-wt/mcp-ingest`), from `86a81f9`, uncommitted.
EXPERIMENTAL, hidden, off by default. Labels: VERIFIED (a test or measurement here), REASONED, UNKNOWN.
Builds on `docs/m7.3b-broker-architecture.md`, `-integration.md` and `-lifecycle.md`; the A0 assurance limit is unchanged
(a same-user shell agent that can run `mind grant` is outside every guarantee; broker authorization is the grant store's state,
not human consent).

## 1. Contract

Enabled only by the hidden flag `mind mcp --isolated-ingest` (implies the broker). It takes effect only when the kernel sandbox is
verified (`SandboxState::Enforced`) AND the broker channel arrived; otherwise the server prints one line and the tool does not
exist. Without the flag the tool is not listed, `tools/call` answers `unknown tool`, and the tool list is byte-identical to the
previous one (VERIFIED, unit test and over the wire). `--broker` alone starts the broker but does not offer the tool (VERIFIED).

`repo_ingest_isolated`, input (`additionalProperties: false`, nothing else is accepted):

| field | meaning |
|---|---|
| `path` | canonical absolute path of a directory root the broker is authorized to serve |
| `spaces` | 1-64 existing space names |

Refused as unexpected arguments (VERIFIED, no worker is started): `grant`, `access`, `ttl`, `fd`, `wall_timeout`, `max_blob_bytes`,
`history`, `paths`. There is no Git support, no path selection and no limit parameter.

Success (`isError: false`, `structuredContent`): `ingested` (the same per-outcome summary `repo_ingest` returns),
`isolation` {`authority`: `static_root`|`grant`, `worker` {seccomp, no_new_privs, tracer_pid, cap_eff, cgroup,
`contained_in_server_cgroup`, cleanup, peak_rss_kb, exit}, `ended_by`, `descendants_killed`}, `context_exchange`
{`manifest_entries`, `known_derivations_reused`}, `resource_policy`, `elapsed_ms`, `sandbox`, `seccomp`.

Failure (`isError: true`): `content[0].text` is the JSON of `structuredContent` = `{error: {kind, message}, persisted}`;
`persisted` is `false` for every kind except `persist_failed` (`"unknown"`: only a failure of the COMMIT itself leaves the outcome open; the write is one transaction, so it is all or nothing, and the failure carries `atomic: true`). Kinds:
`invalid_argument`, `unknown_space`, `root_not_authorized`, `revoked`, `timeout`, `cancelled`, `busy`, `replay_refused`,
`broker_unavailable`, `refused`, `context_refused`, `result_refused`, `confinement_not_verified`, `containment_not_verified`,
`worker_failed`, `broker_io`, `persist_failed`, `not_enabled`, `too_many_files`, `commit_not_authorized`.

## 2. Authorization boundary

* The caller supplies a string. The frontend cannot canonicalize a directory approved after it was confined (Landlock), so it does
  not try: it passes the string through; the broker matches it **exactly** against the roots it derives itself (`CombinedAuthority`),
  opens the directory with `openat2` (no symlinks), checks device/inode against the approved identity and pins it. A subdirectory,
  a parent, a symlink, `..` and a relative path are refused (VERIFIED).
* The broker's authorities are separate (VERIFIED, and a bug found and fixed while testing): **static** = the roots named
  explicitly with `--allow-root`; **grant** = the grant store, re-read for every operation. A grant that was already active when
  the server started is NOT promoted to a static root (it used to be: it then could not be revoked). Where a path is both, the
  static authority governs (VERIFIED: revoking a grant on a static root does not end the operation).
* The tool never consults the frontend's own `McpConfig` root list; the existing `repo_ingest` still does and is unchanged.
* Spaces are resolved by the frontend (names to ids) and bound to the operation; the worker cannot choose them. The operation id is
  chosen by the frontend, used once (replay refused), and binds the stream frames and the context exchange; `check_result`
  validates placeholders against the context this operation sent (M7.3b.3).

## 3. Persistence boundary

**Atomicity (found and fixed in this milestone).** `persist_files` used to be TWO transactions: `record_observation` committed, then
`record_code_observation` ran in a second transaction (each also took its own recording revision). A failure or crash between
them left a committed observation (sources, document assertions, FTS rows) with no derivations (reproduced with a real SQLite
fault and by comparing the contents of every table: `tests/persist_atomicity.rs`, red before the fix). Now
`Store::record_files_ingest` writes both in ONE transaction and ONE revision: the whole logical ingestion commits, or (any error,
or a crash before the COMMIT) none of it does (VERIFIED, also through MCP). `record_observation` and `record_code_observation`
remain for other callers; the in-process `repo_ingest` benefits too (same function) and its reports are unchanged.
The Git path (`persist_git`: git observation, code observation, then relationship resolution per commit) has the same
split and is NOT changed here (out of scope; it needs its own change because the resolution step reads committed state).

**What must hold before anything is written.** The existing assembler and `check_result` accepted the stream; the broker
reported `ended_by = done`; the worker exited with code 0 by itself; its cgroup lies inside the server's own. Every other ending
persists nothing (revoked, timeout, cancelled, worker or broker crash, malformed stream: row contents unchanged, VERIFIED).

**Commit-time authorization lease.** Inside the write transaction, after every statement succeeded and immediately before the
COMMIT, the frontend asks the broker (`CommitRequest{op}`). The broker takes the grant store's shared `flock` FIRST (the lock
`mind grant revoke` needs exclusively), THEN rechecks that the grant is still valid and stays valid for the lease horizon, and
answers `CommitGranted` or `CommitDenied`. A denial rolls the transaction back. After the COMMIT the frontend sends `CommitDone`
and the broker releases the lock. The lease ends at `CommitDone`, a hang-up or the 3 s ceiling (`COMMIT_HOLD_MAX`); the
frontend only commits within 2.5 s of the grant and otherwise abandons the commit. The frontend gains no authority: it neither
reads nor locks the store, it exchanges messages. A static root takes no lock (it cannot be revoked).

## 3b. Revocation linearization (exact)

The linearization point of a revocation against a persistence is **the broker's acquisition of the shared lock in the commit
lease**. Every `mind grant revoke` is ordered either before it (the recheck sees the revocation: commit denied) or after the
`CommitDone` / ceiling (the revocation waits for the lock). Boundaries, each with a deterministic test (the frontend is stopped by
test-only pause files, never by sleeps):

| Revocation happens | Result | Test |
|---|---|---|
| before the operation starts | refused at `Begin` (`root_not_authorized`) | `static_and_dynamic_roots_...` |
| during extraction | broker recheck (100 ms), worker killed, `revoked`, nothing persisted; latency 17-93 ms | `revoking_a_grant_during_extraction_...` |
| during the context exchange | same | `revoking_a_grant_during_the_context_exchange_...` |
| after the worker finished, before persistence (write transaction open, frontend stopped before the lease request) | **commit denied**, transaction rolled back, contents unchanged, `revoked` | `revocation_after_worker_completion_but_before_persistence_...` |
| during persistence (lease granted, frontend stopped before COMMIT) | `mind grant revoke` BLOCKS (asserted after 700 ms), the commit goes through, the revoke completes afterwards: ordered after the commit | `revocation_during_persistence_waits_...` |
| a frontend that stalls past the ceiling | revoke waits at most ~3 s (2.5-8 s asserted), the late frontend finds its lease expired and abandons the commit: nothing persisted | `a_stalled_frontend_cannot_hold_a_revocation_...` |
| after the commit | data stays (revoking never deletes derived data); the next operation is refused | same test as "during persistence" |

Mutation check: with the lock removed from `hold_shared` the "revoke must wait" assertion fails.

**What this does not cover (remaining windows).**
* The microseconds between the broker granting the lease and the COMMIT (inside the lease nothing can be revoked, so this is not a
  revocation race, but a crash of the frontend there leaves a held lock until hang-up).
* Expiry (`--ttl`) is a clock, not an event: a grant is leased only if it stays valid for the 3 s horizon, otherwise the commit is denied.
* A process that edits the grant file without the lock (not `mind grant`): outside A0.
* `mind grant revoke` can be delayed by up to the ceiling by a stalled frontend (availability of revocation, bounded).
* A compromised frontend can ignore the protocol and write the database directly; it already owns the database.

## 4. Resource policy (Phase 2)

Placement is the in-unit cgroup of the previous milestone. No per-operation cgroup limit exists or is configured, and none may
move workers out of the unit. **There is no aggregate per-operation memory limit**: the bounds are the wall clock
(`--ingest-timeout`, default 30 s; the broker's own 300 s is the outer bound), the 64 KiB request / 16 MiB manifest / 32 MiB context
lines, the stream limits (512 MiB total and of content, 32 MiB per blob, 100000 frames) and the structural parse policy. The unit's own `MemoryMax=`/`TasksMax=`, if set, covers the whole tree.
The result says so (`resource_policy`). **Fail closed:** without a configured limit the broker now tries ONLY the process's own
cgroup; if that fails it does not start (before this change it would have fallen back to a sibling cgroup outside the unit), and
each call also verifies that the worker ran inside the server's cgroup, refusing otherwise (`containment_not_verified`).


### 4b. Unscoped ingestion: is the wall clock enough? (no)

The tool has no `paths`, so every call is an unscoped ingest of a whole directory. The wall clock alone does not bound the work or
the frontend's memory sensibly: the real caps are 100000 files, 512 MiB of content (all of it held in the frontend until the
commit, plus the derivation structures) and the clock; a 100000-file tree would run into the 30 s limit after consuming 30 s of
worker CPU and fail late. The in-process tool avoids this with a pre-scan and a 2000-file refusal. **Policy for experimental use:**
the same limit, enforced as the stream arrives: `max_files = 2000` (`MAX_UNSCOPED_INGEST_FILES`), so the 2001st file is refused,
the worker is ended and nothing is persisted (VERIFIED: 2001 files refused after 252 ms; exactly 2000 ingested in 1.0 s;
the in-process tool refuses the same tree). A larger directory cannot be ingested through this tool until it gets a path
selection (a later milestone). No sibling-cgroup fallback was added; per-operation limits are still absent.
Found on the way: the stream assembler admitted `max_files + 1` files (it did not count the file being opened); fixed with a
one-line count (the in-process validation was already exact).

## 5. Revocation (Phase 4)

* The broker rechecks a **grant** authority every `recheck_interval` (100 ms) while the operation runs, whatever the worker is doing,
  and once more at `Done`. A grant that is gone, expired, changed in path/device/inode, or whose store cannot be verified ends the
  operation (fail closed): the worker's cgroup is killed, `Finished.ended_by = revoked`, the frontend returns `revoked` and persists nothing.
* Static authority is never rechecked against the grant store (VERIFIED, distinct from grants).
* Measured (release, 8 trials, revoke during a slow parse at different phases of the interval): time from `mind grant revoke`
  returning until the tool error: **min 16.7 ms, median 60.6 ms, max 93.3 ms** (bound = interval + kill; the cgroup is killed and reaped
  before the report). Debug runs stay under the 2 s test bound.
* Revocation during the context exchange: VERIFIED with a stand-in worker that stalls after reading the request (worker silent in
  the exchange); during extraction: VERIFIED with a real worker and a slow parse. Cancellation and timeout: VERIFIED
  (frontend wall clock, and the broker's wall clock as a distinct ending). Frontend-initiated cancel is not reachable from MCP.
* Replaying an old context or request cannot bypass it: the context is bound to the operation id (the worker refuses another),
  the operation id is single-use, and the decision to persist comes from the broker's `ended_by` for THIS operation.
* A bug found by this work and fixed: after the broker ended an operation itself (revocation, timeout) the frontend's late `Cancel`
  was treated as a protocol violation and the broker closed the connection and exited. Exactly one stray terminal message is now
  tolerated after a broker-ended operation; anything else is still a violation.

## 6. Real-MCP evidence (`tests/mcp_isolated.rs`, debug and release, real Landlock/seccomp/cgroups)

1 tool absent without opt-in / `--broker` alone; 2 present with it, list = old list + the tool last, schema has exactly `path`,`spaces`;
3 static root ingested, found afterwards by `code_search`; 4 a grant added after startup ingested without restart; 5 unauthorized
roots, relative path, unknown space refused, rows unchanged; 6 revoked grant refused; 7 mid-operation revocation (extraction and
context exchange) cancels and persists nothing; 8 malformed stream (garbage manifest; garbage where the record stream must start)
changes no rows; 9 worker SIGKILL: MCP, broker and later calls survive; 10 broker SIGKILL: `broker_unavailable` ("the broker is not
available ..."), other tools keep working, repeated calls fail the same explicit way; 11 a repeated ingest reports reused
derivations and adds no derivation rows; 12 existing tools behave identically (unit test pins the list; `repo_ingest` still works
in an opted-in server; the whole existing suite passes).

## 7. Performance (release, medians of 3, same machine)

| tree | `repo_ingest` in-process | `repo_ingest_isolated` first | repeated (derivations known) |
|---|---|---|---|
| 3 files | 1.0 ms | 14 ms | 6 ms |
| this repository's `src` (~100 files) | 524 ms | 561 ms | 28 ms |
| synthetic, 1800 files | 2144 ms | 2282 ms | 1679 ms |

Fixed cost about 13 ms (cgroup, handshake, spawn); about 7% on larger trees; the repeated run skips parsing. Not measured: trees much
larger than these, memory of the frontend while holding a large stream (the frontend still accumulates the whole result).

## 8. Remaining risks

1. Experimental and hidden; no production default. The tool is a single synchronous call holding the broker link.
2. No aggregate per-operation memory limit (section 4); a worker can use memory until the unit's limit or the wall clock.
3. Fresh-parse semantic correctness remains a trust boundary (`docs/m7.3b-context-exchange.md`).
4. Revocation granularity during a run: 100 ms; at the commit it is exact (section 3b). `mind grant revoke` can wait up to 3 s behind a stalled frontend's lease.
5. Watchdog SIGKILL double fault, system-level units and no-delegation deployments: as in `docs/m7.3b-broker-lifecycle.md`.
6. The stand-in worker hooks exist only in `cargo test` builds (feature `spawn-gate`); absent from the release binary (checked with `strings`).
7. The Git persistence path is still three separate writes (section 3).
8. A directory with more than 2000 ingestable files cannot be ingested through this tool (no path selection yet).
9. `repo_ingest_isolated` writes only the database; unlike `repo_ingest` on Git it writes nothing into the repository.
