# M7.3b parser safety: stack overflow, iterative traversal, structural-parse policy

Labels: **Measured**, **Reasoned**, **Unknown**. Release build, development host.

## 1. The crashes (Measured, reproduced on `dcdc6cb` before the change)
| Input | Size | Exit | Crash site |
|---|---|---|---|
| 20,000 nested braces | 40 KB | 134 (SIGABRT, "has overflowed its stack") | `code::walk`, about 10,270 frames deep on the 8 MiB main stack |
| 30,000 nested parentheses | 60 KB | 134 | `code::walk`, same depth |
| 1,000,000-term `a+a+...` | 2 MB | 134 | `code::count_errors` (first to run; a new `TreeCursor` per level) |
Stack traces from gdb (release binary, symbols only): `Node::kind <- walk <- walk <- ...` (10k
frames) for the first two, `ts_malloc_default <- ts_tree_cursor_new <- Node::walk <-
count_errors <- count_errors ...` for the chain.

Distinction (Measured with the `parse_probe` example, tree-sitter only vs full `code::parse`):
* **Tree-sitter parser recursion: none.** Parsing alone succeeds for all three (20 ms /
  27 ms / 1.2 s; 13 / 15 / 480 MiB).
* **Mindspace recursion: the cause.** `code::walk` and `code::count_errors`, one stack frame
  per tree level, so the depth of the *input* decides the stack use.
* **Other recursive processing: none found.** The markdown path survived 300,000 nested
  `>`, 3,000 nested list levels, 500,000 emphasis markers and 100,000 nested HTML tags
  (in-process, 27-60 MiB). The tree's destruction is iterative in tree-sitter's C code
  (it completed for the 1M-deep tree). The same crash happened in the in-process ingest, so
  `mind mcp` could be killed by one such file today.

## 2. The fix (implemented, uncommitted on `fix/m7.3b-parser-safety`)
* `count_errors` and `walk` are iterative: a `TreeCursor` pre-order traversal plus an explicit
  heap `Vec` of contexts (the enclosing entity's syntax path and qualified name, shared with
  `Rc<str>`). The per-node work moved unchanged into `visit`; the order of visits (named and
  anonymous children, depth first), every value, and the output types are the same.
  Depth is now bounded by memory, not by the thread's stack. No truncation, no limit.
* Side effect: parent strings are no longer cloned for every child.
* Cancellation: the parse had none and has none; unchanged (see 5).

Equivalence (Measured): the recursive implementation is kept as a test-only reference
(`code::tests::reference`) and compared on the 85 real source files of this repository (src and tests) plus nine
truncated (corrupted) variants of each, more than 3,000 entities (asserted), and on generated nested input
(braces, parentheses, chains, modules, impls, nested functions, many items, empty, broken):
`CodeDerivationDraft` equal for all. The existing `code_classification` / `code_structure`
suites pass unchanged.
Regression (Measured): `tests/parser_safety.rs` runs each case in a child process on the small
test-thread stack: 20,000 braces, 30,000 parentheses, 1,000,000 chain, 3,000 nested modules
(all 3,000 kept). On the old code all four children abort with exit 134; on the new code all
pass.

## 3. Structural parsing limits (evaluation only; nothing implemented)
Three different limits, which must not be conflated:
| Limit | Purpose | Status |
|---|---|---|
| max text blob / file size read | bounds reading and content memory | implemented: 32 MiB (`ProducerLimits`) |
| max source size for structural parsing | bounds tree-sitter's memory and CPU | proposed |
| max stream record | bounds one record in flight | implemented: 96 MiB |

Measured memory and CPU of structural parsing (tree-sitter tree and full `code::parse`):
| Input | Size | Tree only | Full parse | Peak RSS | Entities |
|---|---|---|---|---|---|
| ordinary Rust (18,000 items) | 4.3 MiB | 0.8 s | 1.5 s CPU | 254 MiB | 72,000 |
| single-line array of `1`s | 5 MiB | 4.5 s | 7.2 s | 1,486 MiB | 1 |
| random punctuation | 5 MiB | 5.3 s | 7.1 s | 1,050 MiB | 0 |
| 1M-term chain | 2 MB | 1.2 s | 2.1 s | 606 MiB | 1 |
| 20,000 braces / 30,000 parens | 40-60 KB | 20-26 ms | 42-48 ms | 20-22 MiB | 1 |
Per input byte: ordinary code about 60 bytes of RSS, hostile input 200-290 bytes and 1-1.5 s of
CPU per MiB. The memory is the tree-sitter tree itself (tree only 1,476 MiB for the array).
The blob limit alone therefore does not bound a hostile source file: 32 MiB could need about
9 GiB (Reasoned, linear).

How large are real source files? In 94,212 `.rs` files (cargo registry and git checkouts on this
host): 767 are over 256 KiB, 293 over 512 KiB, 63 over 1 MiB, 15 over 2 MiB (generated
bindings), none over 4 MiB.
Proposal (Reasoned from the table): a separate, configurable structural-parse cap of **2 MiB**
(skips 0.016 % of real files; bounds a hostile file to about 600 MiB and 3 s), applied by the
producer; and a tree-sitter progress/timeout callback as a CPU backstop (not deterministic, so
only a backstop).
Keeping text while skipping structure: the text of a source file is stored with its code input,
independent of the parse, so a skipped file still has its content. The existing
`CodeParseStatus::Failed` with `error_count: 1` and no entities can express "not parsed", but:
* there is no field for the reason, so the diagnostic would be implicit (a `skipped` status or a
  `reason` text is a schema decision);
* **`has_code_derivation` treats any stored derivation as done**, whatever its status, so a
  skipped derivation would stay skipped when the cap is raised or the file shrinks until the
  parser identity changes. A skip therefore needs either a status-aware shortcut or a cap-dependent
  identity. This needs a decision before implementation.

## 4. Failure isolation: what the parser can prevent and what needs a process
| Failure | Prevented in-process? | Needs the worker boundary |
|---|---|---|
| Stack overflow from recursion | **Yes** (done for the two known functions) | A backstop for unknown recursion: the worker contains an abort |
| Size-driven memory blow-up | Partly: size cap, pre-checks | Yes for anything the cap misses |
| Tree-sitter allocation failure | No: the C library aborts ("failed to allocate memory") | Yes |
| `RLIMIT_AS` abort | No (Rust aborts on allocation failure) | Yes |
| cgroup OOM kill (SIGKILL) | No | Yes |
| Parser CPU time (5-8 s for 5 MiB) | Partly: a progress callback / timeout | Yes for a hard stop |
| Cancellation during a parse | No: the parse is a blocking C call; observed 6.5 s latency | Yes: kill the worker |
| Panic in other code | `catch_unwind` possible but not reliable with C frames | Yes |
Summary: the iterative traversal removes the only crash reproduced here, but a large class of
failures (allocation failure, OOM kill, uncancellable parsing, timeouts) cannot be handled
inside the process and must be survived by a worker the frontend can kill and replace.

## 5. Remaining crash and exhaustion paths
* Tree-sitter memory and CPU on hostile source (bounded only by a future cap, `RLIMIT_AS`, cgroup).
* Quadratic cost for deeply nested entities: every nested `function_item` copies its source text
  (`text(n)`); not exercised at depth (Reasoned).
* The parser has no cancellation point; cancellation is only as prompt as the next frame.
* Unknown: other grammars or future parsers; behaviour of tree-sitter under `RLIMIT_AS` partial
  failures beyond the abort seen.
