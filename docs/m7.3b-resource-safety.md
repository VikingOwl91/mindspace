# M7.3b.1 resource safety gate: measurements and policy

Labels: **Measured** (run on the development host, release build, fixtures under
the scratchpad: `hostile/*`, built by a script with `git fast-import`),
**Reasoned**, **Unknown**. The per-process numbers come from `/proc/self/status`
(VmHWM = peak RSS, VmPeak = peak virtual size) and `smaps_rollup` (PSS at exit).

## 1. Per-blob policy (implemented in the stream producers only)
* `ProducerLimits.max_blob_bytes`, default `DEFAULT_MAX_BLOB` = 32 MiB of **raw**
  text bytes (not the encoded size; its JSON form can be several times larger, so
  `MAX_RECORD` is 96 MiB).
* **An oversized blob fails the operation** with `Error::BlobTooLarge{path,size,limit}`
  (message: exclude it with `--path` or raise the limit). It is not skipped and
  never truncated: skipping would silently change what is ingested.
* Only blobs/files that extraction would read as text are subject to it; large
  binaries are never read (their declared size is not even looked at).
* Git: the declared size from `cat-file --batch-check` is checked before any
  content is read; the bytes Git returns are checked again. Directories: the file
  size is checked before the read and the read itself is capped at limit + 1.
* The in-process ingest is **not** changed: it has no limit. Compatibility impact
  appears only when the production worker replaces it: a repository with a text
  file over 32 MiB then needs `--path` or a higher limit.
* Hardening found on the way: `parse_batch_stream` added a hostile declared size to
  an offset without a check (`18446744073709551615` wrapped); it is now a saturating
  sum and a typed "truncated batch output" error (unit test).
* Tested: exactly at the limit (accepted, equal to the in-process result) and one
  byte above (typed error, both Git and directory); 1500 small blobs; one blob
  referenced from 40 paths (sent once); a 150 MiB blob refused without being read;
  a 32 MiB + 1 file refused by the directory producer.

## 2. Hostile repositories (Measured; producer / consumer / in-process)
| Fixture | Producer wall, CPU | Producer RSS (VmPeak) | Consumer RSS | In-process RSS | Notes |
|---|---|---|---|---|---|
| 31 MiB single-section text blob | 0.30 s | 154 MiB (235) | 166 MiB | 172 MiB | stream 100 MB (JSON of evidence + assertion + content) |
| 240 MiB of binary blobs | 0.04 s | 11 MiB | 6 MiB | 11 MiB | never read |
| 20 MiB commit message | 0.15 s | 71 MiB | 50 MiB | 70 MiB | spilled, round trip exact |
| path depth 1500 (3000 chars) | 0.05 s | 11 MiB | 8 MiB | 12 MiB | fine |
| 60k tiny .md files | 1.54 s | 53 MiB (158) | 176 MiB | 123 MiB | 420k records, 78 MB |
| 30k commits + 100k-entry tree | 3.71 s | 94 MiB (176) | 340 MiB | 457 MiB | 196 MB stream; tree record spilled |
| 30k tiny .md in a plain directory | 0.56 s | 14 MiB | 71 MiB | 43 MiB | |
| 5 MiB single-line Rust array | 8.0 s, 8.0 s CPU | **1499 MiB** | 26 MiB | 1498 MiB | tree-sitter tree |
| 5 MiB random punctuation as Rust | 7.5 s | **1061 MiB** | 25 MiB | 1061 MiB | tree-sitter tree |
| 20,000 nested braces / 30,000 nested parentheses / 1M-term `a+a+...` | - | **abort** | - | **abort** | stack overflow, SIGABRT |

Where memory grows (Measured):
* **Tree-sitter**: the parse tree alone is 1476 MiB for the 5 MiB array (`parse_probe`
  example: tree only 1476 MiB, full `code::parse` 1486 MiB), about 290 bytes per input
  byte for pathological input, and 4.5-8 s of CPU. The blob limit (32 MiB) therefore
  does not bound memory: a 32 MiB hostile `.rs` would need roughly 9 GiB (Reasoned,
  linear extrapolation).
* **Stack overflow in `code::walk`** (existing code, reproduced in the in-process
  path too): deeply nested input aborts the process. In the MCP server this kills the
  server; in a worker it is contained. A depth limit or an iterative walk is needed;
  not changed here (it would change what is extracted for such input).
* **Consumer**: about 6x the content plus structure; 196 MB of structural JSON
  (commits, 100k-entry tree) became 340 MiB.
* **Producer**: flat (50-100 MiB) for everything except the parser.
* **Cancellation is not prompt during parsing**: the cancel flag is looked at when a
  frame is closed. Cancelled 1 s into the 8 s array parse, the producer stopped
  6.5 s later; on the 60k-file repository it stopped 26 ms after the cancel.
  The frontend must therefore kill the worker for a hard stop (it must anyway).

## 3. Resource limits (Measured, `RLIMIT_AS` via `setrlimit` in a child)
Outcome per limit (ok / typed error / abort):
| Scenario | 64 | 128 | 256 | 512 | 1024 | 2048 MiB |
|---|---|---|---|---|---|---|
| directory, 30k files, producer | ok | ok | ok | ok | ok | ok |
| 60k files in Git, producer | ok | ok | ok | ok | ok | ok |
| 20 MiB spilled commit, producer / consumer | abort / abort | ok | ok | ok | ok | ok |
| 31 MiB blob, producer / consumer | abort | abort | ok | ok | ok | ok |
| wgpu (large Git), producer | typed error from Git | ok | ok | ok | ok | ok |
| wgpu, consumer | abort | abort | abort | ok | ok | ok |
| tree-sitter, 5 MiB hostile `.rs` | abort | abort | abort | abort | abort | ok |
* Allocation failure in Rust is `memory allocation of N bytes failed` (SIGABRT);
  tree-sitter prints `tree-sitter failed to allocate memory` and aborts. There is no
  graceful error from inside the allocator; the process boundary is the handling: the
  frontend sees a truncated stream and reports it. A failing Git child (limit inherited)
  gives a typed error.
* `RLIMIT_AS` limits address space, not resident memory, and the reserved arenas
  of a process make it larger than RSS (VmPeak 158 MiB for 53 MiB RSS). Producer
  limits of 256 MiB suit normal repositories; a 2 GiB limit is needed to survive the
  5 MiB hostile file, which is no real bound on a hostile one. It does not bound total
  system memory (there can be many workers).
* **Concurrent extraction**: four wgpu producers at once: 5.7 s wall (5.3 s single),
  RSS 50-52 MiB each, PSS 42-47 MiB each; no interference. Memory is the sum.
* **cgroup memory limit** is available here (`systemd-run --user --scope -p
  MemoryMax=...`; the user manager delegates the memory controller). It bounds RSS
  (+ page cache): the 5 MiB hostile file was OOM-killed (SIGKILL) at 200M and 400M
  and ran at 2G; the wgpu consumer was killed at 200M and ran at 400M. Whether the
  controller is delegated on other hosts is Unknown. It is the only option here that
  limits real memory.

Recommendation (Reasoned from the above): per worker `RLIMIT_AS` 1 GiB with a
source-file parse limit (about 1 MiB, tree-sitter parse timeout and a depth cap) so
that the parser cannot ask for more, plus a cgroup `MemoryMax` where available; the
frontend sets its own memory budget for the consumer (about 7x the content limit).

## 4. Read-ahead (Measured, 7 interleaved runs, wgpu clone, producer piped to consumer)
| Configuration | Median wall | vs in-process (4.7 s) | Consumer RSS | Sum of peak RSS (both) |
|---|---|---|---|---|
| default pipe (64 KiB) | 6.00 s | 1.28x | 278 MiB | 329 MiB |
| 1 MiB pipe | 5.62 s | 1.20x | 278 | 330 |
| 4 MiB read-ahead | 5.74 s | 1.22x | 282 | 334 |
| 16 MiB read-ahead | 5.42 s | 1.15x | 294 | 345 |
| 64 MiB read-ahead | 5.61 s (5 runs, other session) | - | 283 | 334 |
Other repositories (5 runs): 30k commits + wide tree 4.48 s -> 4.12 s with 16 MiB
(vs 2.87 s in process); 60k files 1.97 s -> 1.63 s (vs 1.02 s in process).
The 1.15x target is not reached for repositories whose extraction is fast and whose
result is big (many files: 1.6x; many objects: 1.4-1.5x), because the consumer's decode
(0.7 s for 78 MB) is then comparable to the extraction itself.
Recommendation: a 1 MiB pipe always (no memory cost, -6 %); 16 MiB read-ahead as a
tunable when the frontend's budget allows (-4 % more, +12-16 MiB); 4 MiB shows no
useful effect and 64 MiB no gain over 16 MiB. 64 MiB is not a default.
