Regressions to state plainly: the 1.15x end-to-end target is met only for small repositories and
roughly for large content-heavy ones (wgpu 1.16-1.22x); repositories with very many small
files or objects cost 1.4-1.6x because the consumer's decode (0.7 s for 78 MB) is comparable to the
extraction. Producer memory is 2-6x lower than in-process; consumer memory is about 0.8x of the
in-process peak and not lower in absolute terms.

## Memory baseline per process (Measured; experimental, not production limits)
Git children were measured through a shim that applied an address-space limit to `git` only, or
to the producer only (Git unlimited).
| Fixture | Producer RSS / VmPeak | Producer passes at `RLIMIT_AS` | Largest Git child RSS | Git passes at `RLIMIT_AS` |
|---|---|---|---|---|
| wgpu | 51 / 167 MiB | 128 MiB | 75 MiB (48 runs) | 128 MiB (fails at 96) |
| Git repo with two 2 MiB hostile sources | 618 / 730 MiB | 768 MiB (fails at 512) | 8 MiB | 32 MiB |
* 1 GiB per process (experimental): passes both producers and both Git children on these fixtures
  with 25-30 % headroom over the hostile producer; it would also be inherited by the Git children
  unless the producer lowers it for them.
* `RLIMIT_AS` is per process and counts address space, not resident memory. An aggregate limit
  needs a cgroup (`MemoryMax`), which counts the producer and its children together: wgpu sums to
  about 51 + 75 = 126 MiB of RSS if the largest Git child runs at its peak, the hostile Git case to
  618 + 8. cgroup limits also kill (SIGKILL) instead of failing an allocation. No production value
  is proposed here.
