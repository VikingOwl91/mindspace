# M7.3b.5b: the confined Git reader

Status: implemented as a library component and test harness. **Not wired into the worker, the broker or any tool**
(those are steps 5c to 5e of `design-m7.3b5-git-worker.md`). Labels: **VERIFIED** (observed in a test or experiment named
here), **REASONED**, **UNKNOWN**.

## 1. What it is

`ingest::confined_git::ConfinedGitReader` reads ONE repository, HEAD only, without ever changing it, inside the sandbox of an
extraction worker. It reuses the existing command runner and the pure object parsers of `ingest::git::GitReader`; it differs
in how the repository is reached and how git is started.

```
broker (unconfined)                       worker (Landlock, non-dumpable, seccomp)            git child
  verifies + pins root  --fd 4-->           ConfinedGitReader::open(root fd, GitExecutable)
  resolves git + ELF interpreter            openat(root, ".git", O_NOFOLLOW)  -> git dir fd N
  (GitExecutable::resolve)                  refuses what v1 cannot confine
                                            Command(exe, env cleared) ----fork----> close_range(CLOEXEC) on 3..
                                                                                    fcntl(N, F_SETFD, 0)
                                                                                    fchdir(root)
                                                                                    exec git  (GIT_DIR=/proc/self/fd/N)
```

| Requirement | Mechanism | Evidence |
|---|---|---|
| 1 One verified, pinned root | The reader takes the root as a `BorrowedFd` (the worker's descriptor 4) and duplicates it. It never opens a path. Verification and pinning stay with the broker (unchanged); this slice has no broker wiring | `open` signature; `absent_descriptors_fail_closed` (no descriptor 4: exit 3) |
| 2 Authority through inherited descriptors | The root arrives as fd 4; the git directory is `openat`ed beneath it; git inherits the git directory's descriptor | `a_git_child_inherits_one_descriptor_...` |
| 3 `/proc/self/fd/N` for children | `GIT_DIR=GIT_COMMON_DIR=/proc/self/fd/<N>`, resolved in the child | same test (the child's environment is printed) |
| 4 Not the worker's `/proc/<pid>/fd/N` | Negative control inside the sandbox: a child started with the parent-pid path fails (`fatal: not a git repository: '/proc/<pid>/fd/5'`) | `every_adversarial_attempt_...` (the `legacy pin style` attempt) |
| 5 No access beyond repository and runtime | Landlock: read/list on the root and the system directories, execute on **git and its ELF interpreter only** | `every_adversarial_attempt_...`; mutation M3 (re-done as mutation M3' against the stabilized rules) |
| 6 No modification | Landlock grants no write; the reader opens nothing for writing; `GIT_OPTIONAL_LOCKS=0` | `reading_head_changes_nothing_...` (byte, size, mode and mtime snapshot, sandboxed and not) |
| 7 No identity marker creation | `repository_id()` is `openat(O_RDONLY\|O_NOFOLLOW)`; a missing marker is `identity_missing` | `the_identity_marker_is_never_created` |
| 8 Linked worktrees and external alternates refused | See section 4 | `linked_worktrees_external_alternates_grafts_and_links_are_refused`, `the_sandboxed_worker_refuses_...` |
| 9 HEAD only | The API has `head()`, object lookup by id, the marker; no ref listing, history walk, branches, remotes or tags | API surface |
| 10 Directory ingestion unchanged | `enter_extraction_worker` has the same rule set as before; the new function is separate; nothing else of the worker was edited | the existing suites (section 7) |

## 2. Git subprocess policy (Phase 3)

One function creates a confined git child: `confined_command` in `ingest/git.rs`.

### Executable
* Absolute path chosen by the caller, `GitExecutable::resolve`: must be absolute, canonicalized, a regular executable file that is
  not writable by group or others, and a 64-bit little-endian **ELF** binary. The `PT_INTERP` string is read from the file and
  canonicalized (the kernel executes the interpreter on the binary's behalf). A script is refused: its interpreter would be a
  third executable.
* `exec_grants()` is the list the sandbox may execute: the binary and, if any, the interpreter. VERIFIED to be exactly what is
  needed: with the system directories read/list-only, git runs with those two grants (all tests).
* No `PATH` lookup (the environment has no `PATH`), no shell (`Command` with an argument vector), no dashed helper programs
  (`GIT_EXEC_PATH=/nonexistent`).

### Environment
Cleared, then exactly: `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_NO_REPLACE_OBJECTS=1`, `GIT_TERMINAL_PROMPT=0`,
`GIT_OPTIONAL_LOCKS=0`, `GIT_PAGER=cat`, `GIT_PROTOCOL_FROM_USER=0`, `GIT_ATTR_NOSYSTEM=1`, `GIT_NO_LAZY_FETCH=1`,
`GIT_EXEC_PATH=/nonexistent`, `LC_ALL=C`, `GIT_DIR`, `GIT_COMMON_DIR`. Cleared rather than filtered: the in-process reader removes
`GIT_*` variables, but `PATH`, `HOME`, `LD_*` and `XDG_*` would still pass. VERIFIED: `GIT_DIR`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`,
`GIT_OBJECT_DIRECTORY`, `GIT_WORK_TREE`, `GIT_CONFIG_COUNT/KEY/VALUE` and `PATH` set in the parent do not reach git
(`replace_refs_and_a_hostile_object_environment_...`; the child's environment is printed by the spy script).

### Configuration
* System and global configuration: not read (`GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_GLOBAL=/dev/null`; the latter also replaces the XDG file).
* Repository-local configuration: **read**, because git needs it (`core.repositoryformatversion`, `extensions.objectFormat`);
  every exec- or network-capable key a hostile `.git/config` could set is overridden on the command line, which wins over the file:
  `core.fsmonitor`, `core.hooksPath`, `core.alternateRefsCommand`, `core.pager`, `core.askPass`, `protocol.allow=never`, `gc.auto`,
  `maintenance.auto`, `core.useReplaceRefs=false`, `submodule.recurse=false`, `fetch.recurseSubmodules=false`,
  `core.untrackedCache=false`, `core.sshCommand`, `core.gitProxy`, `uploadpack.packObjectsHook` (empty).
* Hooks: `core.hooksPath=/dev/null`; the commands used never run hooks anyway.
* Filters, textconv, external diff, `gpg.program`, `credential.helper`, aliases: only consulted by commands the reader never runs
  (`checkout`, `diff`, `status`, `cat-file --filters/--textconv`, signature verification). Not pinned because there is nothing to pin;
  the kernel stops them regardless (see the evidence below).
* Submodules: a gitlink is listed as mode `160000` by `ls-tree`; nothing recurses into it.

### Replacement and grafts
* Replacement refs: `GIT_NO_REPLACE_OBJECTS=1` and `core.useReplaceRefs=false`. VERIFIED (a `refs/replace` entry that would read
  HEAD as its parent is ignored).
* **Grafts are not switched off by either setting** (VERIFIED with git 2.56: `info/grafts` still rewrites the parent list with both).
  The reader therefore **refuses a repository that has `info/grafts`**. Shallow files are honoured as written.

### Descriptors
Between `fork` and `exec` (async-signal-safe calls only): `close_range(3, ~0, CLOSE_RANGE_CLOEXEC)` marks every descriptor above stderr
close-on-exec in the child's copy of the table; then the git directory's descriptor alone is made inheritable; then `fchdir(root)`.
The worker's own descriptors keep their flags. VERIFIED: a descriptor deliberately left inheritable in the parent does not reach the
child, and the only descriptor above stderr the child holds is the git directory (mutation M1 makes the test fail). Descriptors are
not closed (only flagged), because closing them would also close the pipe the standard library uses to report a failed `exec`.

### What is demonstrated about execution
* Positive control: a repository configured with an executable helper for `core.fsmonitor`, `core.sshCommand`, `core.pager`,
  `diff.external`, filters, a shipped `post-checkout` hook and an alias **does** run the helper when `git status` is allowed to
  (the canary file is written). The same repository read by the reader (sandboxed or not) writes nothing.
* Finding: with git 2.56, none of these keys fires for the plumbing commands used (`rev-parse`, `ls-tree`, `cat-file`, `rev-list`,
  `for-each-ref`, `worktree list`, `config --list`), even without any `-c` override. So the `-c` list is defence in depth; **the kernel
  is the barrier**. UNKNOWN for other git versions; that is why the barrier does not depend on git's behaviour.
* The kernel alone: with the pins switched off, `git -c core.fsmonitor=<canary> status` in the sandbox does not start the helper
  (execute is denied), and the worker cannot execute `/bin/sh` or any program but git.

## 3. Kernel prerequisites and limits (environment-dependent)

* Linux with **Landlock ABI 3 or newer** (the tests read the ABI and skip with a message below 3), `close_range` with
  `CLOSE_RANGE_CLOEXEC` (Linux 5.11; the reader fails closed if the call is unavailable), seccomp.
* Tested on kernel 7.2.14 (zen), git 2.56.0 at `/usr/bin/git`, glibc dynamic linking. Not tested: a statically linked git
  (no interpreter; `exec_grants` then has one entry), musl, other architectures (the ELF reader is 64-bit little-endian only and
  refuses anything else), git older than 2.44 (`GIT_NO_LAZY_FETCH` is ignored by older versions).
* Landlock cannot restrict the **read** of files outside the allowed trees that the system directories contain (`/usr`, `/lib`,
  `/lib64`, `/etc/ld.so.cache`, `/dev/urandom`, the worker's `/proc` entry).

## 4. What v1 refuses (fail closed, with a message)

| Case | Detection |
|---|---|
| `.git` missing (bare repository) | `fstatat` on the root descriptor |
| `.git` is a symbolic link | `fstatat(AT_SYMLINK_NOFOLLOW)`, `openat(O_NOFOLLOW)` |
| `.git` is a file (a linked worktree) | `fstatat` |
| `.git/commondir` (the git directory of a linked worktree) | beneath the git directory |
| `.git/worktrees` (the repository has linked worktrees) | beneath the git directory |
| `objects/info/alternates`, `objects/info/http-alternates` | beneath the git directory, no link on the way |
| `info/grafts` | as above |
| a symbolic link as `HEAD`, `config`, `objects`, `refs`, `packed-refs`, `info`, `shallow` | `fstatat(AT_SYMLINK_NOFOLLOW)` |
| an object format other than SHA-1 | `git rev-parse --show-object-format` at `open`; every object id the reader accepts is exactly 40 lowercase hex digits. The tree parser reads 20-byte entries and would misread SHA-256 silently (see `m7.3b5c-verified-git-transport-plan.md`, section 2.3) |

The refusal of a repository that has linked worktrees is stricter than necessary for HEAD-only reading (the worktrees live
outside the root and the reader never lists them); it is the simplest rule that satisfies "linked worktrees are refused in v1".
A link elsewhere inside the git directory (below the top level) is not walked: it cannot leave the authorized root (Landlock
decides by inode), but it can point at another place inside it. The in-process reader walks the whole directory; this one does not,
to keep the cost independent of the object count. Residual, see section 6.

## 5. Findings about the existing code (not changed here)

1. **The directory worker could execute files beneath `/usr`: fixed in the stabilization commit `fae2f79`.**
   `worker_rules()` granted `Rights::Read` on `/usr`, `/lib` and `/lib64`, which is Landlock's read set *including execute*, while
   the documentation said "no execute". VERIFIED before the fix: `exec:/bin/sh` was ALLOWED in a worker confined with those rules;
   a started shell stayed inside the worker's domain (it could not read `/etc/passwd`, write into the root or list `/home`), so it
   was surplus authority rather than an escape. The system directories are now `Rights::ReadList` (read and list) for every worker,
   and the git sandbox adds execute for exactly the two files of `GitExecutable::exec_grants`. Regression test:
   `extraction_worker::the_directory_worker_cannot_execute_a_program`.
2. The in-process `GitReader::repository_id` creates the marker; the confined reader never does. A repository without a marker
   cannot be read by it (`identity_missing`).
3. `GitReader::pinned` with `/proc/<pid>/fd/<n>` paths cannot serve a sandboxed worker's children (design document section 3;
   re-verified here by the negative control).

## 6. Residual risks

* A repository can ship a marker equal to a victim repository's id (design decision D3, unchanged).
* A symbolic link below the top level of the git directory that points inside the root is followed by git.
* Partial clones: `extensions.partialClone` with a missing object makes git try a lazy fetch. `GIT_NO_LAZY_FETCH=1` and the denied
  sockets and execution prevent it; an attempt in this environment did not reproduce a fetch even without the variable, so the
  claim "a promisor repository cannot trigger a fetch" is REASONED, not demonstrated.
* Git versions other than 2.56.0 were not tested; a hostile configuration key that a different version consults for plumbing
  would meet the kernel confinement, not a pin.
* The deadline kills the git child it started; a grandchild would survive the reader. Inside the sandbox a grandchild can only be
  git (the only executable), and the broker's cgroup (step 5d) removes the whole tree. Not re-verified here without a broker.
* Resource limits (object counts, memory) are the stream limits of step 5c. A repository with a huge HEAD tree is read in full.

## 7. Tests

`tests/git_confined.rs` (16 tests + 1 ignored performance observation). Real-kernel tests start `mind git-probe`, a hidden
subcommand that exists only with the `spawn-gate` feature (the same test-only pattern as the broker gate; the release binary contains
none of it). The probe confines itself exactly like the extraction worker (+ execute for git and its interpreter) and prints one JSON
line; the tests judge from outside. Mutation checks (each made the named tests fail, then was reverted): M1 skip the close-on-exec
sweep, M2 do not clear the environment, M3 keep execute under `/usr`, M4 do not refuse grafts, M5 do not make the git directory's
descriptor inheritable. The switch that turns the `-c` pins off (`ConfinedExec::apply_pins`) exists only with the
`spawn-gate` feature; a production build has no way to start a confined git without them.
