# M7.3b.5c plan: verified Git-object transport (design only, nothing implemented)

Status: plan. Basis: `design-m7.3b5-git-worker.md` section 4.4/4.5/4.7, the confined reader of 5b
(`m7.3b5b-confined-git-reader.md`) and the code as of the M7.3b.5b stabilization. Labels: **VERIFIED**
(observed in code or by running it here), **REASONED**, **UNKNOWN**. Scope of 5c: what travels from a
worker to the frontend and how the frontend decides to believe it. Not in 5c: the worker mode, the
broker, the MCP tool (5d, 5e).

## 1. The problem 5c solves

A directory worker cannot lie about content: the frontend recomputes the SHA-256 of every file
(`check_code`: `sha256_hex(content) != content_hash`). A Git worker today could: the stream carries
*parsed* objects, and the frontend never recomputes a Git object id. VERIFIED by reading
`Assembler::accept` (`stream.rs`) and `extract::check_result`:

* a `Commit`/`Tree`/`Tag` record is `{ item }` with a parsed struct; the checks are `is_oid` (40 or 64
  lowercase hex), uniqueness, counts and the phase order. Nothing relates `item.oid` to `item`'s content.
* a `Blob` record is `(oid, size)`; `BlobContent` fills the content later for blobs with derivations. The code
  input is checked by its SHA-256 `content_hash`, but nothing binds `blob_oid` to that content.
* `GitCommitData` is lossy (`parse_commit`: continuation headers such as `gpgsig` are dropped, the message is
  trimmed, time zones are folded into a timestamp), so the id cannot be re-derived from the parsed record.

Consequence: a compromised worker could report a commit id with any tree, parents or message, or attach a
different blob's content to a path, and the database would store it as that repository's history. The
authority of a worker is "reads one repository"; 5c makes its *claims* checkable from what it sends.

## 2. Design

### 2.1 Raw objects for commits, tags and trees; blobs by content
* New records `RawObject { kind, oid, bytes }` for **commit, tag and tree** (they are small and structural).
  The frontend is the only party that parses them: `parse_commit`, `parse_tag`, `parse_tree` (existing pure
  functions) run in the frontend on the verified bytes. The parsed `Commit`/`Tree`/`Tag` records disappear from
  the Git worker's stream (the in-process path keeps producing them from its own, trusted, reads).
* **Blobs:** the id of a blob is `H("blob <len>\0" + content)`. A blob with a derivation already travels with
  its content (`BlobContent`), so the frontend can recompute the id from the bytes it receives. Blobs without a
  derivation (large, binary, non-source) travel as `(oid, size)` and **cannot** be re-hashed without their
  bytes: they stay unverified, documented, and labelled in the result (`blobs_unverified: n`). A size cap
  decides what is sent in full (see 2.5); sending every blob would multiply the transport volume.
* The worker chooses *which* objects to report, never *what an object contains*: an object id binds its bytes.

### 2.2 Frontend recomputation
For each raw object: `id' = H(header(kind, len) + bytes)`; reject unless `id' == oid`. Then parse and check
**consistency between objects**, all before anything is persisted:
* a commit's `tree` is a reported tree (or a tree already stored for this repository); every parent is a reported
  commit or an announced boundary (see 2.6);
* a tree's entry targets are reported objects of the right kind (blob, tree) or gitlinks (`160000`, not followed);
* a tag's `object` is a reported object of the declared type;
* `ViewCommits`, refs and tags point at reported commits/tags; each blob in `git_source_versions`/derivations is
  reachable from a view commit's tree **by the path claimed** (the path -> blob_oid binding is what
  the code structure rides on);
* the HEAD-only v1 scope: the object set equals the closure of HEAD's commit (its tree, the trees below) plus the
  commits reached through the parents the stream announces; anything else is refused as fabricated.
All of this uses the existing parsers and the `Assembler` state; the new part is the relation checks.

### 2.3 SHA-1 and SHA-256 object formats
VERIFIED here (git 2.56.0, `git init --object-format=sha256`):
* **The stored model is format-agnostic.** The git tables use `TEXT` oids with no length constraint
  (`migrations/0003_git_ingest.sql`), `is_oid` accepts 40 or 64 hex, and the two lengths cannot be confused.
  No migration is needed for either format, and no table records the format (derivable from the oid length).
* **The pipeline is not.** `parse_tree` reads fixed 20-byte entries (`nul + 21`). On a SHA-256 repository the
  current reader returns *40-digit tree-entry ids that name no object* and leaves leftover hash bytes in the next
  entry's mode, without an error. This is a **silent misreading in the existing in-process path today**; it is
  not caused by 5b. (The 5b confined reader refuses a repository whose `git rev-parse --show-object-format` is
  not `sha1`, and every object id it accepts is exactly 40 lowercase hex digits; test
  `a_sha256_repository_is_refused_instead_of_misread`.)
* The frontend would need SHA-1 (no crate in the tree except `sha1_smol` in the cargo registry, which is not a
  dependency; `sha2` is) and a collision-detecting variant is preferable (git itself uses one). New dependency =
  an explicit decision (D2 in the 5 design).

**Decision proposed: defer SHA-256 in 5c.** 5c supports SHA-1 only, with the frontend refusing any object id that
is not 40 hex digits and the worker refusing at `open`. SHA-256 support is a later slice with these parts, none
needed for SHA-1: a hash-width parameter for `parse_tree` (derived from the *repository's* format, never from
a per-record guess), a SHA-256 recompute (the `sha2` crate is already a dependency), a repository-level
`object_format` field in the Git header record and a test matrix over both formats. A guard in the in-process
`parse_tree` (refuse a tree whose id is 64 digits until that slice) is a **separate small fix** and recommended
independently of 5c.

### 2.4 Stream validation and placeholder provenance
* New phase ordering for the Git worker stream: header -> refs -> raw commits/tags/trees -> blobs (+ content) ->
  views/current sets -> end. The `Assembler` already enforces phase order and uniqueness; `RawObject` joins the
  `Objects` phase.
* `Record::CodeInput.reused` is currently directory-only (placeholders for derivations the requester announced
  as known). The assembler refuses `reused` for Git (VERIFIED: "Directory operations only"). 5c lifts that for
  Git with the same rule, keyed by `(repository_id, blob_oid, identity)` from the context exchange: a
  placeholder is accepted only for a blob the frontend announced as known **and** whose id was verified in this
  stream (a reused derivation must not let an unverified blob id ride along). The extractor version being
  part of the announced identity (M7.3b.5b stabilization, `mind-code@4`) means a stale derivation is never
  announced.
* The result of `check_result` records what was verified (`objects_verified`, `blobs_unverified`) so the tool
  can report it.

### 2.5 Limits (all new, explicit; producer side stops early, consumer side enforces)
Proposed starting values for review (D4 of the 5 design), per Git operation:
`max_refs` 10,000; `max_commits` 20,000; `max_trees` 200,000; `max_tags` 10,000; `max_raw_object_bytes` 1 MiB
(a commit, tag or tree larger than that is refused, not truncated); `max_files` 2,000 (as `repo_ingest`
for an unscoped tree); `max_blob_bytes` as today (32 MiB); the stream totals as today (512 MiB, 100,000
frames). Counts are enforced when a record is accepted, not at the end (today the assembler pushes without a
count check; VERIFIED). A repository above a limit is refused with `too_large` before most of the work is done;
v1 is HEAD-only, so the commit/tree counts are bounded by HEAD's closure.
Object-size accounting: header `size` for blobs is checked against the bytes received (a blob whose declared
size differs from its content is refused).

### 2.6 Rejection of inconsistent or fabricated history
Refused, each with a named error (`object_verification_failed`, `inconsistent_history`):
* an object whose recomputed id differs from its claimed id;
* a duplicate id with different bytes (uniqueness is already enforced per kind; extended across kinds);
* a commit whose tree or a parent is unknown and not an announced boundary; a tree entry whose target is neither a
  reported object nor a gitlink; a tag whose target type disagrees with the object;
* a cycle (a commit that is its own ancestor): impossible with verified ids (an id cannot contain its own hash),
  but checked cheaply because parsing is cheap;
* a path -> blob binding that the verified trees do not contain;
* objects outside HEAD's closure (v1 scope), refs not pointing at reported objects, counts above the limits;
* any non-40-digit id (SHA-256 deferred).
Boundary commits: a v1 HEAD-only extraction reports HEAD's commit with its parent ids but not the parents'
objects; the parent ids are stored as ids (as today) and are marked as *unverified boundary* in the result. This
is a deliberate cut: the parents' contents are not needed for HEAD's tree, and verifying them would turn
HEAD-only into a history walk.

## 3. Tests (before implementation)
Parity: the same repository through the in-process path and through the verified stream gives identical tables
(the differential method of the Directory worker). Hostile streams (crafted in-process, no worker needed): a
commit with a wrong id; a tree whose entry points at an unreported blob; a blob content that does not hash to its
id; a derivation attached to a path whose verified tree entry names another blob; a duplicate id with different
bytes; a tag with a mismatched target type; a `reused` placeholder for an unverified blob; counts and byte limits at
the boundary and one over; a SHA-256 id in every record kind; a forged "boundary" parent; objects outside HEAD's
closure. Mutation checks for each guarantee (remove the recompute -> the hostile-id test fails).

## 4. Order of work inside 5c (each independently testable)
0. **Guard first (separate, small):** refuse non-SHA-1 trees in the in-process `parse_tree` / reader, so SHA-256 is
   rejected everywhere, not only in the confined reader. (Behavior change of an existing path: needs a decision.)
1. `RawObject` record, frontend hash recomputation for commit/tag/tree, unit tests on hostile streams.
2. Relation checks (tree -> blobs, commit -> tree/parents, tag -> target, path -> blob binding).
3. Blob verification where bytes are sent; `blobs_unverified` accounting; size agreement.
4. Count/size limits at accept time (producer and consumer side).
5. `reused` placeholders for Git with provenance; extractor-version-aware announcements (already in place).
6. Parity differential: in-process vs verified stream, then the exit criteria of the 5 design (fmt, clippy, full
   suite, release and real-kernel runs, repeated runs, one mutation check per guarantee).

## 5. Open decisions for review
* **D-SHA256:** defer (proposed) or implement in 5c. Deferral needs the guard in step 0 to be a real refusal.
* **D-SHA1 crate:** `sha1_smol` (small, no collision detection) vs a collision-detecting crate vs shelling out (rejected
  in design D6). Recommendation: a collision-detecting implementation, justified because the whole purpose of the
  check is to distrust the worker.
* **D-unverified blobs:** accept `(oid, size)` blobs as unverified (proposed, labelled) vs send everything up to a
  cap. The cap trades transport volume against verification coverage.
* **D-boundary:** HEAD-only parents as unverified ids (proposed) vs refusing a repository with history until a
  history scope exists.
* **D4 limits:** the numbers in 2.5.

## 6. Risks
* Transport volume: raw trees are larger than parsed ones (binary entries); bounded by the limits above and by the
  HEAD-only scope, measured in 5c before the limits are fixed.
* Frontend CPU/memory for parsing and hashing hostile-but-valid streams: bounded by the same limits; the frontend is
  not sandboxed against parser bugs more than it is today (the pure parsers already run on git output in-process).
* A verified id does not make a repository *trustworthy*, only the stream *faithful*: a hostile repository can still
  contain hostile content; and a repository can ship a marker equal to another repository's id (D3, unchanged).
* SHA-1 collisions remain possible in principle (as in git itself); a collision-detecting hash narrows, not closes, that.
