# M7.3b.5c: verified Git-object transport (implemented)

Status: implemented as a library component; **not wired** into the worker, the broker or any tool (5d, 5e). Scope: HEAD.
Labels: **VERIFIED** (observed in a test named here), **REASONED**, **UNKNOWN**. Plan: `m7.3b5c-verified-git-transport-plan.md`.
Code: `ingest/gitverify.rs` (pure verification), `ingest/stream.rs` (`Kind::GitVerified`, `emit_verified`, the assembler),
`ingest/confined_git.rs` (`head_closure`, the producer side). Tests: `tests/git_object_format.rs`, `tests/git_verified.rs`.

## 1. Step 0: non-SHA-1 repositories are refused

* **The defect (VERIFIED on the unmodified code, git 2.56):** `parse_tree` reads fixed 20-byte entries. Ingesting a SHA-256
  repository did not fail. It stored tree entries with 40-digit target ids while the commit and tree ids were 64 digits, and
  a `mode` column holding raw hash bytes. Nothing flagged it.
* **The fix:** `GitReader::require_sha1()` (`git rev-parse --show-object-format`) runs first in `extract_git_with_reader` and
  `stream_git_with_reader`, before the identity marker is created and before anything is read or emitted. The error is the new
  `Error::UnsupportedObjectFormat { format }`: "unsupported repository: object format `sha256` is not supported (only SHA-1
  repositories can be ingested)". The confined reader uses the same check at `open`.
* **Evidence:** `tests/git_object_format.rs` on a real SHA-256 repository: refused in the head and history scopes, every table of the
  database unchanged, no marker written into the repository; a SHA-1 repository still ingests and every stored entry id names a
  real object. Red before the fix, green after. SHA-256 parsing is **not** implemented (excluded by the task).

## 2. The contract: `Kind::GitVerified`

A new operation kind. The existing `Kind::Git` stream (parsed records) is unchanged.

| Record | Meaning | Verification state |
|---|---|---|
| `Begin { kind: git_verified }`, `GitHeader` | operation, session, repository identity, spaces | as for `Git` |
| `Head { symbolic, commit_oid }` | the HEAD claim: branch name (or none) and commit id | **claim about repository state**; the commit's CONTENT is verified |
| `RawObject { kind, oid, size, hex }` | the raw bytes of one commit or tree (lowercase hex) | **content verified** (id recomputed) |
| `Blob { oid, size }` | a blob the trees name | **reference verified**; size is a claim |
| `BlobContent` + `Chunk`, `Derivation`, `CodeInput` | blob content (with its parse) | **content verified** when the bytes arrive (blob id recomputed) |
| `CodeInput { reused: true }` | placeholder for a derivation the requester already has (no parts) | content still travels and is verified; path -> blob binding verified |
| `Remote` | configured remotes | worker-asserted repository metadata (not content-addressed) |
| `End { counts }` | completion; `raw_objects` counts the new record | counts compared with what arrived |

Refused in this kind: `Ref`, `Commit`, `Tree`, `Tag`, `RefEvent`, `ViewCommits`, `CurrentCommits`, `CurrentTags` (the receiver builds
commits and trees from raw bytes; the scope is HEAD, so there is no ref listing, history, tag or view). A `RawObject`/`Head` outside this kind is
refused. Phase order: header, head, objects, blobs, remotes, body.

Errors are not records: a failed verification ends the operation with `Error::InvalidExtraction("... verification ...")` and returns
**nothing**, so persistence is never reached (VERIFIED: `a_rejected_transport_stores_nothing...`, every hostile stream returns `Err`, database
row counts unchanged).

### What the receiver builds
From the verified bytes, with the existing parsers: the HEAD `GitCommitData`, every `GitTreeData` of the closure, one `HEAD` ref observation,
`view_commits = current_commits = [HEAD]`, no tags, no ref events. This is the in-process HEAD scope minus what HEAD-only cannot know (worktree
heads, tag releases, history objects). `current_tags = None` leaves release memories untouched; `current_commits = Some([HEAD])` retires memories
derived at other commits, as the in-process HEAD scope does. Remotes are carried because persistence marks every remote not listed as no longer current.

## 3. Verification rules (`gitverify::verify_head`, `Assembler::finish_verified`)

1. Every id is exactly 40 lowercase hex digits (SHA-256 refused).
2. Only commit and tree objects (blobs and tags are not part of the closure); at most one commit.
3. **Id recomputed**: `SHA-1("<kind> <len>\0" + bytes)` must equal the claimed id (so a wrong id, a wrong type and a wrong size all fail here);
   the declared `size` must equal the content length (checked before decoding).
4. No duplicate ids (also across the stream).
5. The head commit must be among the objects and be a commit. It is parsed **by the receiver** and its headers checked strictly:
   `tree`, then `parent`s, then `author`, `committer`; malformed ids refused.
6. The closure is walked from the commit's tree (explicit stack, no recursion): each tree is parsed **strictly** (known modes only, no
   truncation, no empty/`.`/`..`/`/`-containing/`.git` names, no duplicates), each subtree must have been sent and be a tree, gitlinks are not followed.
7. **Reachability**: every received object must be reached from the head commit; a stray tree or a second commit is refused.
8. **Path -> blob binding**: a derivation or code input at (commit, path) must name exactly the blob that the *verified* tree has at that path, at the *head* commit.
9. **Blob rows** are exactly the blobs the verified trees name (an extra row is an unreferenced object, a missing one a blob without size).
10. **Blob content** that travels (blob row content, derivations, code inputs) must hash to its blob id and its recorded size must equal the content.
11. Limits (section 5), at record acceptance and during the walk.

Three states are reported (`VerificationSummary`, returned in `ReadStats.verification`): *content verified* (commit, trees, blobs whose bytes arrived),
*reference verified* (named by a verified, reachable tree: all blob ids), *external* (parent ids and gitlink ids: named by verified objects, themselves
not verified). Test: `an_honest_transport_is_accepted...` (content-verified objects = 1 + trees; content-verified + unverified blobs = reference-verified blobs;
2 external references: one parent and one gitlink).

**Parents outside the scope** are kept as ids in the commit (`git_commit_parents` stores ids, no foreign key to a parent commit row) and counted as
external references. A parent commit *object* in the stream is refused (`commit object ... limit`), whatever it claims to be.

## 4. Hashing implementation decision

SHA-1 is a local implementation (about 40 lines; FIPS 180-4), **without collision detection**.

* Evaluated: a collision-detecting implementation (`sha1collisiondetection`), `sha1`, `sha1_smol`. In this build only the source of `sha1_smol`
  is present in the offline cargo registry; none of the three is a dependency of the crate, and none of the candidates available here detects
  collisions except `sha1collisiondetection`, which is not available. Adding a crate gains nothing without detection and costs a dependency decision.
* Verified: the standard vectors, the block-boundary lengths (55, 56, 63, 64, 65 bytes, values taken from `sha1sum`), the empty blob/tree ids, and
  a differential test against `git hash-object --stdin` over nine inputs including 40 KB and all byte values.
* **Recommendation:** replace `gitverify::sha1` by a collision-detecting implementation when a dependency can be added; the function is the only place.
  SHA-256 repositories are refused, so no second hash is needed.

## 5. Resource limits (`VerifyLimits`, all explicit; the stream ceilings stay)

| Limit | Value | Rationale |
|---|---|---|
| commit objects | 1 | HEAD only; parents are not transported |
| tree objects | 20,000 | ~4x the directory count of the Linux kernel tree; larger repositories are refused, not truncated |
| tree entries (all trees together) | 200,000 | ~2.5x its file count |
| blob records | 100,000 | blob rows are held in memory by the assembler |
| one raw object | 256 KiB | a tree of ~6,500 entries; its hex fits one 1 MiB frame, so no spill is needed |
| all raw objects | 64 MiB | ~20x the real tree bytes of the largest repositories above; hex doubles it to 128 MiB, inside the 512 MiB stream ceiling |
| directory nesting | 64 | git paths rarely exceed 20 |
| traversal work (entry visits) | 1,000,000 | bounds the expansion of a tree DAG (a tree may name one subtree many times); ~12x the file count |
| path length | 4,096 | PATH_MAX |

Stream ceilings (unchanged): frame 1 MiB, total 512 MiB, 100,000 frames, record 96 MiB; content/derivation limits of `ExtractionLimits`.
Enforcement: sizes are checked from the declared `size` **before** decoding; counts at record acceptance; entries/depth/work during the walk; allocations
are bounded by the limits above (checked arithmetic with `checked_add`/`saturating_add`). The producer (`ConfinedGitReader::head_closure`) enforces the same limits
while collecting and stops early. Tests: exact boundary and one-over for every limit (`limits_are_enforced_at_the_exact_boundary_and_one_over`,
`stream_limits_apply_at_record_acceptance`, `the_producer_stops_early_at_its_limits`).

## 7. Trust assumptions that remain

1. **Existence is not verifiable.** Hash verification proves the stream is *internally consistent* and that no object's content is misrepresented: a worker cannot
   put different content under a real object id. It does **not** prove an object exists in the authorized repository: a compromised worker can invent a
   self-consistent commit and tree (new ids, new content) and report it as HEAD. The worker's authority is "reads one repository"; what it *says it read* is trusted
   to that extent.
2. **The HEAD claim**: which commit is HEAD, its symbolic name, and the remotes are worker assertions (not content-addressed). A worker may name a stale or different
   real commit as HEAD.
3. **Unverified blobs**: blob ids/sizes whose bytes do not travel (binary, large, non-source) are reference-verified claims only.
4. **External references** (parents, gitlinks) are ids only.
5. **SHA-1 collisions**: no detection (section 4).
6. **Marker/identity**: a repository can ship a marker equal to another repository's id (decision D3 of the 5 design, unchanged).
7. A verified id does not make the repository's *content* trustworthy.
