# M7.3b.5e plan: opt-in isolated Git ingestion through MCP (design only, nothing implemented)

Status: plan. Basis: the committed 5a-5d work (`m7.3b5b-*`, `m7.3b5c-*`, `m7.3b5d-git-worker.md`) and the existing directory tool
`repo_ingest_isolated` (`src/mcp/isolated.rs`, `docs/m7.3b-mcp-isolated-ingest.md`). Labels: **VERIFIED** (observed in a test or in the code read for
this plan), **REASONED**, **UNKNOWN**. The assurance limit of the whole line is unchanged: a same-user shell agent that can run `mind grant` is outside
every guarantee, and broker authorization is the grant store's state, not human consent.

## 1. What 5e adds, and nothing else

One new MCP tool, `repo_ingest_git_isolated`, behind its own hidden opt-in flag, wired to the 5d path. No new authority class, no new grant, no
repository format beyond SHA-1, no schema migration, no change to any existing tool's name, schema or description, and no change to the default tool list.

## 2. Gates (all must hold, otherwise the tool does not exist)

| Gate | Where it is decided | Failure |
|---|---|---|
| `--isolated-git-ingest` (hidden; implies the broker, like `--isolated-ingest`) | the human's command line | the tool is not listed and cannot be called (as `repo_ingest_isolated` today) |
| An approved git executable: `--git-exe <absolute path>` given together with the flag | the human's command line, resolved by stage 1 BEFORE the fork | startup prints one line and the tool is NOT offered; the server keeps running without it |
| Verified kernel sandbox of the frontend and the broker channel | stage 2, as today | the tool is NOT offered |
| Usable cgroup containment | the broker's start | the broker is not started; every operation is refused `broker_unavailable` (VERIFIED in 5d) |
| The root is authorized | the broker, per operation (static root or active grant, re-read now) | `root_not_authorized` |

The flag alone is not enough and no default executable is assumed: **there is no search of `PATH` and no hard-coded location.** If `--git-exe` is
absent the tool is not offered (the same rule that `--isolated-ingest` applies to its own prerequisites).

### Where the executable path comes from, and where it cannot
* It is read from the server's own command line (or a configuration file the operator owns) in stage 1, resolved with `GitExecutable::resolve`
  (absolute, canonical, regular file, executable, not group/other writable, ELF, interpreter found), stored in the broker's `BrokerConfig.git`, and
  handed to the worker in the broker-built argv. The sandboxed frontend never sees it as input and cannot change it.
* **The MCP request has no field for it.** The tool schema is closed (`additionalProperties: false`): `path` and `spaces` only. A test sends
  `git_exe`, `executable`, `env`, `args`, `grant`, `limit` and expects a schema refusal.
* The debug environment variables used by the test harness (`MINDSPACE_BROKER_GATE_GIT*`) exist only with the `spawn-gate` feature; a test asserts the
  release binary contains none of the hook strings (done for 5d: VERIFIED zero occurrences).

## 3. Tool contract

`repo_ingest_git_isolated`

* **Input:** `{ path: string (canonical absolute path of the repository ROOT, the directory that contains `.git`), spaces: [string] (1..64) }`.
* **Scope:** HEAD only (the 5c/5d contract): the HEAD commit, its trees and blobs; parents and gitlinks stay external, unverified references. Tags,
  branches, history, linked worktrees, alternates and SHA-256 are not offered and are refused with a named error.
* **Success** (`structuredContent`, text mirror): `persisted: true`, `commit_state: "COMMITTED"`, `atomic: true`, the repository id (the broker's), the
  head commit, the symbolic ref, counts (trees, blobs, files derived, code derivations new/reused), and a `verification` object:
  `content_verified_objects`, `content_verified_blobs`, `reference_verified_blobs`, `unverified_blobs`, `external_references`. The description
  states what is NOT verified (existence in the repository, the HEAD claim; see section 8).
* **Failure** (`error.kind`, `persisted`, `commit_state`):

| `error.kind` | When | `persisted` / `commit_state` |
|---|---|---|
| `invalid_arguments` | schema violation, unknown field (including any attempt to name an executable) | false / NOT_STARTED |
| `root_not_authorized` | the broker does not serve this root, or its grant is gone | false / NOT_STARTED |
| `git_unavailable` | the broker has no approved executable (cannot happen when the tool is offered; kept for a broker restart with another configuration) | false / NOT_STARTED |
| `unsupported_repository` | linked worktree, bare, `.git` link, alternates, grafts, worktrees (the broker's `check_layout`) | false / NOT_STARTED |
| `identity_missing` | no `mindspace-repository-id`; the message says to ingest once with `mind ingest` (the human's in-process CLI, not a fallback of this tool) | false / NOT_STARTED |
| `unsupported_object_format` | SHA-256 (the confined worker refuses at open) | false / NOT_STARTED |
| `too_large` | a 5c limit (trees, entries, blobs, raw object size, depth, work) | false / NOT_STARTED |
| `object_verification_failed` / `inconsistent_stream` | the frontend's verification of the stream failed | false / NOT_STARTED |
| `revoked` | the grant was revoked during extraction or the commit lease was denied | false / NOT_STARTED or ROLLED_BACK |
| `broker_unavailable` / `containment_not_verified` | no broker, no cgroup containment, the worker did not run inside this server's cgroup | false / NOT_STARTED |
| `timeout` / `cancelled` / `worker_failed` | wall clock, client cancel, worker death | false / NOT_STARTED |
| `commit_outcome_unknown` | `CommitOutcomeUnknown`: the data may be committed; the handle is discarded; the message says to restart the server and ingest again (it reuses what was committed) | "unknown" / UNKNOWN |

  The mapping is the one of `repo_ingest_isolated::error_of`, extended with the Git causes; `commit_state` keeps the three-valued meaning.
* **Persistence:** `persist_git_with_lease` (5d): ONE transaction and ONE recording revision, the broker's commit-time lease taken immediately
  before the COMMIT, a denial rolls back. The result is persisted only if the broker reports `ended_by = done`, the worker exited cleanly and its
  cgroup lies inside this server's cgroup (the existing containment check).

## 4. Reuse, not reimplementation

* Frontend: a new module `mcp/isolated_git.rs` that mirrors `isolated.rs` for the tool definition, the argument checks and the error mapping, and
  calls `extract_git_via_broker` and `persist_git_with_lease`. `IsolatedIngest` (link, lock, poison flag) is shared: one operation at a time on the
  one broker link, whichever tool started it.
* `McpConfig::with_isolated_git_ingest(link, ...)`; `tools/list` includes the new tool only when it is set. VERIFIED today: the default listing and the
  `--isolated-ingest` listing are covered by existing tests; 5e extends them and asserts they are byte-identical when the new flag is absent.
* Broker: `BrokerConfig.git` is set in `watchdog_main` from the stage-1 value (today it is `None`, so the production broker refuses Git: VERIFIED
  `a_broker_started_the_production_way_without_a_git_executable_refuses_every_git_operation`).
* No in-process fallback exists anywhere on the path: every failure above is an explicit error.

## 5. The executable and the ELF interpreter: what is actually pinned (evidence)

The question: do the resolver's checks remain valid if the filesystem changes between configuration and the worker's execution?

| Window | What is checked / bound | What an attacker who can write to the path can do | Evidence |
|---|---|---|---|
| operator command line -> stage 1 | `GitExecutable::resolve`: absolute, canonical, regular file, executable, not group/other writable, ELF, interpreter from `PT_INTERP` canonicalized | nothing is held open; the result is a PATH (and the interpreter's path) | code |
| stage 1 -> worker start | the worker calls `resolve` again on the broker-built argv | a replacement file that passes the same checks is accepted: **identity (device/inode) and content are not compared with what stage 1 saw** | code (REASONED); no test pins it |
| worker start -> exec (confined) | Landlock rule on the INODE of the binary and of the interpreter, created by opening the path before `restrict_self` | **replacing the path with another file** (rename): the new inode has no execute right in the worker's domain: git does not run, the operation fails closed. **Modifying the same inode in place**: the granted inode still executes the new content | VERIFIED: `a_binary_replaced_after_the_confinement_is_not_executed`; the limit is pinned by `a_binary_modified_in_place_after_the_confinement_still_runs_a_documented_limit` |
| the interpreter | granted by inode as well; the kernel opens it by the path recorded in the ELF at `exec` time | same two cases as above | REASONED (same mechanism; only the binary was exercised) |
| libraries | read-only rules on the system directories; not pinned individually | libraries are read, not executed through the rule; a writable library directory under the system directories would be a system-compromise scenario | REASONED |

Consequences, stated without broadening the claim:
1. After the worker has confined itself, a **swapped** executable cannot run (fail closed). A **modified-in-place** one can, so the guarantee is
   about the inode, not the content.
2. Between configuration and worker start the guarantee is the path checks only. A same-user attacker who can rewrite a file the user owns, or write into
   its directory, defeats it; the resolver checks the file's mode but **not its owner and not its parent directories**.
3. None of this protects against a git binary that is itself malicious or vulnerable; the worker's domain (read-only, no network, no other execute)
   limits what such a binary can do, it does not make it trustworthy.

5e must therefore (required, small, testable): (a) refuse an executable or any of its parent directories that is writable by anyone but root or
the owner of the server process **and** require the file to be owned by root or that user; (b) record `(dev, ino, size)` and a SHA-256 of the binary and of the
interpreter at stage 1, pass the expected identity to the worker, and have the worker compare it on the descriptor it opens before it confines itself
(this closes the stage-1 -> worker window and the in-place modification before confinement; the in-place modification AFTER confinement remains a limit
unless the binary is also executed through the verified descriptor, `fexecve`, which Rust's `Command` does not offer; to be evaluated, not assumed);
(c) flip `a_binary_modified_in_place...` to the new, stronger behaviour only for the part that is actually closed. Until (a) and (b) exist the tool
description must say "the executable is trusted by path".

## 6. Operation identity, restarts and replay

* The client chooses a fresh UUIDv7 per operation; every frame, the manifest, the context and the lease are bound to it. A stream or context from
  another operation is refused (VERIFIED: `replay-op` and the `git_context` tests).
* The broker refuses a reused operation id while it remembers it (a ring of 4096 ids, **VERIFIED for Git**: `a_git_operation_id_cannot_be_reused...`).
  After a broker restart or after 4096 operations an old id is forgotten, so a `Begin` with an old id would be accepted: this cannot confuse two
  requests, because the frontend never reuses an id and anything recorded for an old operation is bound to that old id; it is therefore a property of
  the client, stated here, not a guard of the broker.
* A commit lease is single-use and belongs to the operation that ended `done` (VERIFIED: `a_commit_needs_the_lease_of_its_own_operation`).

## 7. E2E acceptance criteria (through a real MCP client)

The existing `tests/mcp_isolated.rs` harness drives the real server over stdio. For each criterion a test, written first and shown red:
1. Default `tools/list` is byte-identical to today's (no flag); with `--isolated-ingest` alone it is today's; with `--isolated-git-ingest --git-exe …` it adds exactly one tool.
2. Without `--git-exe`, or with a relative path, a path that is no ELF, or a group-writable file: the tool is not offered and one line says why.
3. `tools/call` with `git_exe`/`executable`/`env`/`args`/`grant`/`limit`: refused by the schema; nothing runs.
4. Success on a static root and on a dynamically granted root (granted after the server started): `commit_state: COMMITTED`, one recording revision, the
   verification object, the same derived structure as `mind ingest` of the same repository (differential, as in 5d).
5. Every error kind in section 3 is produced by a real cause (unsupported layouts, missing marker, SHA-256, not authorized, revocation during and before persistence,
   containment unavailable, timeout, cancel via `notifications/cancelled`), each with `persisted: false` and an unchanged database.
6. `commit_outcome_unknown` via the existing store hooks keeps the three-state semantics.
7. Mutations of the 5d/5e guards (the 15 of 5d plus: tool listed without the flag; executable taken from the request; persistence before `Finished`) are caught.
8. systemd (`systemd-run --user`, `Delegate=yes` and `Delegate=no`): start, a successful operation, SIGTERM during an operation, `systemctl stop` after a watchdog
   SIGKILL, and cancellation each leave no worker, git child, watchdog or cgroup tree; the tool works or is refused with `containment_not_verified`, never silently outside the unit.
9. The release binary contains none of the test-hook strings (list as in 5d) and none of the Git worker's misbehaviour modes.
10. fmt, clippy, the full suite, the targeted release suites and 5 repeats of the concurrency-sensitive ones.

## 8. Residual assumptions (must stay in the tool description and the docs)

* **Existence and authenticity are not verified** (5c): hash checks prove the stream is internally consistent. The HEAD claim, the symbolic ref and the remotes
  are the worker's assertions. 5e MAY narrow the HEAD claim by having the broker read `.git/HEAD` and the ref file (or `packed-refs`) itself through the
  pinned root, with plain file reads and no git, and compare the commit id with the stream's `Head`; it would still be a snapshot (a ref can move between the
  read and the worker's read) and would not cover reftable repositories. Not required for 5e; stated so the claim is not made implicitly.
* The identity marker is repository content and can be forged by a hostile repository.
* SHA-1 without collision detection; unverified blobs are `(oid, size)` claims; a non-UTF-8 text blob is not interpreted.
* The executable is trusted as described in section 5.
* No aggregate per-operation memory limit beyond the unit's own; the stream, parse and 5c limits and the wall clock are the bounds.
