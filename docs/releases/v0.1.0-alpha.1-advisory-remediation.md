## Findings, exposure and remediation options

### SQLite: RUSTSEC-2026-0459

The fresh initial `cargo audit` reproduces the failure, exit 1: `rusqlite 0.40.2` → **`libsqlite3-sys 0.38.2`**, bundled **SQLite 3.53.2**, in both normal default and noembed graphs. The upstream advisory identifies local crafted database + sibling WAL page-size mismatch exposing uninitialized page-cache bytes, CVSS 4.0 **6.8 medium**. Affected bundled releases are 0.6.0–0.38.2; fixed crate threshold is >=0.39.0, SQLite >=3.54.0. See [RustSec SQLite advisory](https://rustsec.org/advisories/RUSTSEC-2026-0459.html).

Relevant entrypoints include ordinary CLI/MCP/library opening (`src/storage/sqlite.rs:378-414`), WAL-aware doctor/setup inspection (`:290-329`), and ownership recognition/admission (`src/storage/sqlite/ownership.rs:426-592`). Filesystem permissions do not validate database bytes; read-only/WAL-aware opening is not malicious-page immunity. An explicitly selected less-trusted DB/WAL pair reaches the bundled engine in both variants. No direct repository-text-to-arbitrary-database route or exploit was demonstrated.

Changing only the system SQLite would leave the bundled engine unchanged. Removing embeddings would also leave SQLite affected. Forcing a transitive 0.39 crate into the old rusqlite dependency would violate its native dependency requirement. The chosen owning-dependency upgrade preserves `bundled`, `functions` and `hooks`; no advisory suppression, feature bypass or custom SQLite fork was introduced.

### rustix: RUSTSEC-2026-0486

Initial **rustix 1.1.4** is affected by the unsound zero-length get/list-xattr buffer handling; fixed >=1.1.6, unaffected <1.0.0. The advisory supplies no CVSS severity. See [RustSec rustix advisory](https://rustsec.org/advisories/RUSTSEC-2026-0486.html).

Default normal paths include the optional direct Linux/embeddings dependency and tempfile → safetensors → Candle. The ordinary noembed normal/build graph excludes rustix, but the unchanged deny policy scans all features. Mindspace's explicit production use is `statfs`, not an affected xattr call; no application exploit was demonstrated. That limited reachability did not waive the policy failure. Updating the existing compatible 1.x dependency closes its affected range in the full locked graph.
