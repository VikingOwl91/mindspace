## 4. Publication and artifact safety boundary

The accepted [S3e publication contract](../m8-s3e-publication-design.md), [S3e.1 contract](../m8-s3e1-writer-fencing-design.md) and [architecture R01–R17 matrix](../m8-s3e-architecture-decision.md) are unchanged. Accepted4a–4c prerequisites do not implement a publisher. [Rejected4d evidence](../m8-s3e4d-reconciliation-planning.md) still records native fatal-read/UUID incompatibility despite rollback: its patch is not an accepted baseline or workaround. No new independent qualification clears that rejection here.

Private document storage/staging is not ordinary memory ingestion; neither is canonical knowledge publication. Public eligibility requires the authorized atomic replacement/head/index/receipt/citation operation with applicable old-writer/old-reader/diagnostic compatibility. Existing legacy APIs cannot be used to publish M8 content while avoiding those gates. Lexical-only publication is not an R11 exemption.

Current migration17 admits only passive plans, and CLI rejects activation (`migrations/0017_passive_fence_plans.sql`; `src/cli/ownership.rs:900–934`). Normal retrieval does not federate staging (E1). Old clients are still an unresolved **publication** boundary; they are not proven universally safe by successful legacy retrieval, a schema floor, a restart instruction or lack of a receipt. G4 must verify the promoted ordinary artifact's actual routes and default tool list. Any active path, staging influence or test-only activation is a release stop; merely calling it unsupported cannot make it safe.

**Exactly one recommended next engineering slice: quiesced backup/restore and pre-upgrade rollback qualification, with an operator runbook using existing interfaces.** No additional ordinary Git implementation slice is justified by current evidence. T1 is a scope decision, not a request to begin a second production feature.

The source mechanism motivating T2 is precise: migrations acquire IMMEDIATE transactions **per version** (`src/storage/sqlite.rs:1051–1083,1118–1126`). A failed multi-version upgrade can retain an applied, committed prefix. This is not proof of corruption, nor whole-upgrade atomic rollback. Future schemas are refused (`sqlite.rs:915–940`). The existing closed-store backup test (`tests/private_sqlite.rs:496–525`) checks one space, M6 count and integrity after MAIN copying; it does not qualify live-WAL backup or older-binary rollback.

T2 acceptance criteria:

1. Define supported **offline/quiesced** operation: operator accounts for and stops every CLI/MCP/library writer before backup/restore. File inspection or a missing receipt cannot prove quiescence. No active writer fence is added.
2. Qualify a consistent method and list its real tool prerequisites. Never copy only a live MAIN while acknowledged data may remain in WAL; never recommend deleting sidecars as cleanup. Preserve recoverable committed WAL state and test the selected method after abrupt process exit as well as clean close.
3. Preserve original DB and exact old binary **before the first open by the new version**. Work on copies and restore to a separate path. Backup/restore files/directories must be private from creation, with measured modes and no hardlink alias to the original; do not chmod existing user databases as a shortcut.
4. Populate memory lifecycle/current/as-of/history, spaces, Git source/commit/blob/path refs and scope. Compare restored data, M6 accounting, integrity/FK and CLI/MCP retrieval after reopening. Exercise copy failure, malformed backup and refused recovery without damaging the original; document retry/diagnosis.
5. Qualify each expressly supported populated older-schema origin with its actual old binary: upgrade a clone, test failure/retry/valid migration-prefix behavior, then old-binary reopening of a **restored pre-upgrade copy**. Never promise schema downgrade or running an old binary against the upgraded file. If origins/binaries are unavailable, retain UNKNOWN and explicitly restrict upgrade support instead of asserting compatibility.
6. Deliver reviewable runbook and retained disposable-fixture evidence, with supported filesystem/runtime/operator assumptions. If existing mechanisms prove insufficient, report the concrete failing operation before proposing any production change.
