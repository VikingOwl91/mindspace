## 6. Fresh installation and private initialization

The source-only install route was exercised on this developer host with a fresh signed archive, isolated XDG data/state, temporary binary prefixes and no models. Both ordinary feature sets function for Git/lexical retrieval. The current CLI still reports internal `0.5.0`; metadata alignment to public `0.1.0-alpha.1` remains release work. No crates.io/prebuilt package claim is established.

`SqliteStore::open` uses `create_dir_all` and `Connection::open` without private creation modes (`src/storage/sqlite.rs:376–418`); `initialize` delegates to it (`src/lib.rs:40–55`). We initialized the default XDG path, ingested generated Git content, then held a real MCP connection open after `memory_create`. Live permissions were inspected before closing the connection:

| 022 | 0755 | 0644 | 0644 | 0644 |
| 000 | 0777 | 0644 | 0644 | 0644 |
| 077 | 0700 | 0600 | 0600 | 0600 |

All three cases retained/reopened their data with integrity/FK checks passing; no model directory appeared. These are **passing measurements of a failing privacy property**, not privacy acceptance. Modes depend on caller umask. With traversable ancestors other local users can read retained text/history; umask000 also leaves the newly created application directory world-writable. The evidence root itself was private and no cross-user disclosure/exploit was attempted. Private HOME/XDG ancestors may mitigate access but do not establish private creation by Mindspace.

Concurrent first initialization returned one explicit busy error among four processes. Later retry was logically idempotent and the final schema/integrity were complete. The exact lock phase is not instrumented, so it is UNKNOWN whether it arose during WAL setup or migration admission. Treat it as a disclosed contention/refusal result, not four successful initializations or a proven corruption defect. A bounded Alpha runbook can require init before starting clients; do not mask errors or relax serialization.
