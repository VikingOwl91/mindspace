## 5. Findings and applicability

### F1 — bundled SQLite memory exposure: release blocker

**Confirmed affected dependency / policy failure; exploitation not demonstrated here.** `RUSTSEC-2026-0459`, aliases `CVE-2026-119375` / `GHSA-72w2-rjgg-q729`; scanner CVSS 4.0 score **6.8, medium**. Frozen `Cargo.toml:32` enables rusqlite's bundled feature; both normal default and no-embeddings dependency graphs resolve `rusqlite 0.40.2` → `libsqlite3-sys 0.38.2`. The fetched, checksum-verified amalgamation declares **SQLite 3.53.2**. This is not an advisory against an unused system SQLite package.

The authoritative advisory describes a crafted database plus sibling WAL whose page size differs from the main database, causing ordinary queries to return uninitialized page-cache bytes. It requires local files supplied by a less trusted party and the victim opening them; it is not evidence of remote unauthenticated exposure. Common library/CLI/MCP opening uses `src/storage/sqlite.rs:378-399`, including WAL activation. A user-selected/imported/restored crafted DB/WAL pair can reach the affected engine in either build variant. No route from ordinary repository text directly to attacker-controlled database/WAL bytes was demonstrated.

Existing 0600/0700 creation, safe parent checks, allowlisted repository isolation and trusted offline backups reduce exposure opportunities. They do **not** validate database page contents or remove the dependency finding. A system SQLite update, dropping embeddings, warning users or passing recovery tests cannot clear this frozen bundled implementation's mandatory advisory gate.

Required future remediation: resolve a compatible patched rusqlite/libsqlite3-sys combination; advisory's fixed threshold is `libsqlite3-sys >=0.39.0` bundling SQLite >=3.54.0. Do not force an incompatible transitive override. Verify actual selected native version and both build variants, data/recovery compatibility and unchanged privacy behavior on a new candidate. No exploit or patch was executed in this slice.

### F2 — rustix extended-attribute unsoundness: policy blocker

**Confirmed affected dependency / deny failure; application exploit reachability not demonstrated.** `RUSTSEC-2026-0486` / `GHSA-jh2m-fhpj-3vr7`; classified **unsound**, no CVSS score supplied by the advisory. Version 1.1.4 is affected. Six `rustix::fs` get/list-xattr functions can mark unwritten memory initialized for a zero-length buffer; safe Rust may reach undefined behavior. Fixed threshold: **>=1.1.6**.

The default normal graph includes rustix directly and through tempfile/safetensors/Candle. The normal no-embeddings graph contains no rustix; tests/all-features remain covered by the existing deny policy. Frozen Mindspace source's only explicit production rustix call is `fs::statfs` in `src/retrieval/semantic/cache.rs:100-102`. A textual scan of application source plus 5,867 fetched dependency `src/**/*.rs` files, excluding rustix's own definitions, found affected-name call patterns only in libc FFI declarations. No affected Rustix call site was found. This is bounded source evidence, not a formal alias/dispatch reachability proof or permission to suppress the advisory.

`cargo audit` prints this as an allowed warning; `cargo deny`'s unchanged policy rejects it as an error. That difference is recorded, not converted to PASS. A future compatible rustix >=1.1.6 resolution must pass the unchanged policy. A noembed-only invocation does not waive the existing all-features release gate.

### F3 — paste maintenance warning: retained residual risk

`RUSTSEC-2024-0436`, `paste 1.0.15`, **unmaintained informational warning**, no vulnerability or CVSS assigned; no patched version listed. It is a compile-time procedural macro in optional tokenizer/Candle/gemm chains. Current scan also shows a direct tokenizers route, broader than deny.toml's old “only candle-core/gemm” comment. No runtime exploit is established.

Audit reports the warning; deny's existing `unmaintained = "workspace"` policy does not fail this transitive-only maintenance issue. No suppression was added. Retain the actual dependency-chain warning and revisit upstream replacement separately; it is not the reason for this slice's BLOCKED decision.
